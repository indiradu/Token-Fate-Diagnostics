# Selective K/V caching for LLaDA-8B-Instruct (2026-11-04/05)

**STATUS: complete** (GPU 2026-11-05 00:03 to 02:44, 2.7 h, one claim, GPU released; nothing committed or pushed). Pre-registration: `PREREGISTERED.md` (Part A and B before any GPU decode, Part C addendum before any Part C decode). Words. WORD LOCK = which blank (masked) positions get a token written in a call (saves calls). REPRESENTATION FREEZE / cache = which rows have their K/V cached and skipped (saves compute per call). This campaign tests the cache side. Row types: prompt rows, written answer rows, blank rows (in the 16-row window, beyond the window inside the current 32-block, in later blocks). LLaDA-8B-Instruct, bf16, temperature 0, block 32, MATH (MATH-500 questions), Part A at 256 and 512 tokens, Part C at 512.

## The answer in plain words
1. **What tells us a cached row has gone stale (Part A, 40 MATH train questions, dense Conf-0.9 decodes, 256 and 512 tokens).** The best single signal is *exposure with the cached query*: how much attention the row (using the query stored in the cache, so without recomputing the row) puts on positions written since the row was cached, summed over the calls since. Its AUROC for "K/V changed by more than 10%" is 0.79-0.82 pooled (layers 22-31: 0.79; layers 11-21: 0.82; layers 0-10: 0.82; 512 tokens). It beats age (0.66-0.69) by +0.12 to +0.16 in every layer group and beats the accumulated window attention mass (0.74-0.79) by +0.02 to +0.06 (intervals above +0.02 in two of three groups). It does NOT beat plain distance to the nearest new write by the pre-registered rule: it wins in layers 22-31 (+0.024 to +0.047) and loses in layers 0-10 (-0.06 to -0.05; distance 0.87 there) and is a small win in layers 11-21 (+0.009 to +0.028, below the +0.02 bar at its lower end). Using the fresh query instead of the cached one costs nothing (0.787 vs 0.784 in layers 22-31): the cached query is enough. Row class carries most of the information (class + age alone: held-out AUROC 0.886 in layers 22-31; adding exposure 0.910, adding distance 0.893).
2. **Staleness is not rare.** The noise floor is exactly zero (an identical repeated forward is bit-identical; so is a row-subset recompute), so the 0.05 and 0.10 cut-offs are conventions, not noise-anchored. After ONE call, in layers 22-31 (512 tokens) the median relative change of K/V is 0.037 for prompt rows, 0.049 for written rows, 0.15 for blanks in later blocks, 0.27 for blanks beyond the window and 0.37 for blanks in the window; 18% / 29% / 66% / 90% / 91% of those rows already exceed 0.10. In layers 0-10 the medians are 0.005 to 0.065. A cache that waits is using K/V that are visibly off; the methods work anyway because answers are robust to that (Part C: answers unchanged within noise).
3. **Elastic's one-tracked-row probe does track global drift.** The as-coded trigger is `cosine_similarity(a, b, dim=1)` on a (batch, 32 heads, tracked rows, keys) tensor, i.e. across the HEAD axis at every key, then a plain mean over rows and keys (verified by reading the shapes; the keys version is `dim=-1`). In a dense decode (fresh attention now vs fresh attention one call ago) it correlates 0.55 (Spearman) with the share of stale rows in the layers above it (0.62 with the global share; keys version 0.47) and fires (cosine < 0.9 at some layer) on 36% of calls. It says how much drifted, not which rows: as a per-row score its AUROC is 0.65-0.70, below exposure.
4. **Which ingredient buys the speed (Part C, MATH 54 questions, 512 tokens, one process, one timed repeat; speeds = ratio of summed seconds).**
   - *Caching the far rows and refreshing densely only at block starts is the whole story*: 1.84x [1.69, 1.99] over the same decode with every row every call (W16-dense), with only about 10% of the rows computed. EOS truncation adds 1.07x [1.03, 1.14] and 7% fewer calls. The window decode itself (word-lock change) is neutral: W16-dense 1.02x [0.96, 1.10] of Conf-0.9, calls 0.99x.
   - *Elastic's adaptive trigger costs speed against that simple schedule*: 0.91x [0.86, 0.97] (it recomputes 607 of about 640 rows at a trigger, on 42 calls per answer). Its answers are not worse (net +6 [0, +12] vs the block schedule; not resolved).
   - *Our row-selective refresh* (score at layer 8, rows above an exposure threshold rejoin at layer 9) is faster than the trigger at the lower thresholds (r60 1.12x [1.04, 1.20], r80 1.07x [1.00, 1.15]; r90 0.93x) and equal to the block schedule (r60 1.015x [0.97, 1.07]); it does not beat it. Best cell: selective-r60 2.04x [1.91, 2.19] vs dense Conf-0.9 (block schedule with EOS: 2.01x [1.89, 2.14]); correct answers 17 vs 15 for dense Conf-0.9 (net +2 [-3, +8]). Every cell is inside the answer resolution (about +-4 of 54).
   - *Why 10% of the rows give only about 2x*: a call with 59 rows costs 38.7 ms against 85 ms for 620 rows (a fixed 34 ms per call plus 0.08 ms per row): at this size a call is limited by reading the 16 GB of weights, not by rows. Further cutting rows buys little; fewer calls (the word lock) is the other lever. Calls went UP 19% when the far cache was added (stale rows make the window need more calls), and EOS truncation removed 7% of that.
5. **Parity with the official generator.** Our engine on the official model object (manual bf16 softmax) reproduces the official tokens, call counts, query rows, tracked rows and trigger layers exactly on 3/3 questions (155/148/141 calls, 40/35/26 trigger calls); on our HF model with the manual softmax 3/3 as well; the every-call control equals the official full-recompute baseline 3/3. With the fused SDPA kernel (used for all Part C cells) 0/3 are token-identical (first difference in the written rows at calls 9/25/15, with the query rows, tracked rows and trigger layers identical up to there) and SDPA decodes finish in 8-19% fewer calls. So the port is logically exact and the attention kernel changes which tokens are written; Part C cells are internally consistent but not token-identical to official Elastic-Cache.

## What was done
- `src/regret_remasking/selective_cache.py`: `SelectiveEngine` (per-layer x/q/k/v caches; computed row set can grow mid-forward) and `decode_selective` (official word lock: Conf-0.9 in a window of W blanks, `min(threshold, max)` rule, first-EOS truncation, leftover blanks become EOS). Switches: `window`, `far_mask_cache`, `eos_truncation`, `refresh` in {trigger, selective, every_call, block, none}, `trigger_cos` {elastic_heads, keys}, `gamma`, `track_num`, `attn_impl` {sdpa, manual}, `score_layer`, `exposure_theta`. Official semantics kept: a trigger at layer l makes rows join at layer l+1 from their CACHED layer-(l+1) inputs, so K/V actually refreshed start at layer l+2 (tests show this is close to but not equal to a dense forward; refresh from layer 0 is exactly dense).
- `src/regret_remasking/toy_llada.py` (tiny LLaDA-shaped model for CPU tests), `tests/test_selective_cache.py` (13 tests). No existing file was changed; the existing sparse runtime and `paper_decode.py` are untouched (suite: 386 passed = 373 + 13).
- `orchestration/`: manifest builder, Part A capture (`partA_capture.py`: drift against snapshots at s in {1,2,4,8,16} for every row and layer, computed on the fly inside a wrapped attention call), collector, analyzer, `parity_gate.py` + `official_instrumented.py` (diagnostic copy of the upstream loop that logs per call), `calibrate_theta.py`, `run_partC.py`, `analyze_partC.py`, claim/chain scripts. `validation/`: CPU parity of the port against the OFFICIAL generator on a tiny model built from the official modeling code (call by call, 4 gamma values with mixed trigger layers, multi-write calls, block caching off), capture checked against brute-force definitions, noise floor, GPU parity JSONs.

## Deviations and things to know
- **Part A questions are not the collect_mc `math_train` split as briefed**: its 54 L1-4 questions are the held-out `longlen` `math_l14` set and 36 of its 80 L5 questions are the Test-4 fresh set. 20 L5 (from the 44 free ones) + 20 L1-4 (from unused MATH-500 L1-4 questions), overlap with every held-out pool 0 (`manifests/audit_A.json`). One of 40 questions (prompt of 861 rows) was skipped at 512 tokens: the K/V/Q rings (13.4 MB per row) do not fit beside the model. It is included at 256.
- The pre-registered noise-floor check came out as exactly zero, which does not anchor the thresholds; drift quantiles per class and layer are in `results_partA.md`. The standalone noise step crashed once (autograd); it ran at the end of the 512 collection instead.
- Part C adds one control cell not in the brief (W16-dense: window-16 word lock + EOS truncation, no cache) and three selective cells (thresholds at 60/80/90% recall of stale rows, fit on the Part A train questions at 512). The ladder needs the control, otherwise the speed of the window decode and of the cache cannot be separated.
- SPARSE-none (our existing sparse runtime) runs 0.914x of dense; the new engine (persistent full-size K/V workspaces, only the computed rows are copied in) has no such overhead (W16-dense 1.02x of dense with every row every call). Proposed cheap fix for the old runtime (NOT applied): keep full-size K/V workspaces resident across calls and `index_copy_` only the active rows, instead of `x.clone()`, `out = x_work.clone()` and re-gathering all locked K/V (`index_select` + `index_copy_`) on every layer of every call.
- The selective cells refresh on almost every call (about 160 per answer): at layer 8 some cached row crosses the threshold nearly every call; the threshold decides how MANY rows rejoin (104 / 195 / 276 per call at r60 / r80 / r90), not whether any do.
- Part C is one timed repeat in one process; speed ratios within about 5% are not resolved. 54 questions resolve answer differences only above about +-4. Dense Conf-0.9 got 15 of 54 right; per stratum (27 each) numbers are indicative only. The timing includes `log_calls` counters only (no device-to-host copies of written rows).

## Predictions that failed (details in PREREGISTERED.md, Outcome section)
Noise floor (predicted 0.002 mean, got exactly 0); blank-row stale shares (90% and 66% vs 8% and 6% predicted); Elastic probe Spearman (0.55 vs 0.25 [0, 0.5]); "exposure beats distance" (not by the rule); SDPA parity (0/3 vs >= 1/3); selective refresh counts ordered r60 > r80 > r90 (they are all about 160 per answer); "selective-r80 beats the trigger by the reading rule" (faster by 1.07x but loses 4 net answers).
