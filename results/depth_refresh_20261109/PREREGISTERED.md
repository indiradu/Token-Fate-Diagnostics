# Does a depth- or row-selective refresh restore the answers the S32 representation cache loses? (written 2026-11-09 before any quality decode of these cells)

**Words.** WORD LOCK = C-0.9 everywhere (which blanks are written per call). REPRESENTATION CACHE = S32: query rows = the current block's blanks + rows written on the previous call; prompt rows, older written-answer rows and later-block blank rows are read from the K/V of the last dense call; dense call at every block start; first-EOS truncation. PARTIAL REFRESH (new, `SelectiveConfig.partial_every_k / partial_layer / partial_join`, default off): on a non-dense call, the selected cached rows (`all` / `context` = prompt + written rows / `blank` = later-block blank rows) rejoin the computation at layer l0 from their stored layer inputs, so layers l0..31 are recomputed for them and written back to the store; layers below l0 keep the cached K/V of those rows. `partial_every_k = 1`: every non-dense call is partial. Dataset HumanEval 0-163 (gen 512), LLaDA-8B-Instruct bf16, RTX 5000 Ada, one timed repeat, one process per stage, arms rotated per question, warm-up on question 0, in-process references D:C-0.9 (dense word lock) and S32:main.

**Why these cells (evidence in hand).** (1) `stale_cause_20261108`: random K/V noise of the same per-row, per-layer norm as the staleness costs nothing (N1 vs dense +2 [-5.5, +9.5]; N1 - P-stale +11 [+2, +20]), so the damage is not the size of the error; with only the blank rows stale (B-stale) the loss is -2 [-9, +5], with only the blank rows computed and prompt/written rows cached (nofar, earlier) +1, with everything stale -9. (2) Oracle repair: no single row class restores the first divergence (best single class 6/17, all blank rows 7/17, all rows 15/17). (3) Drift per layer is smaller below layer ~10 (relative K change of prompt rows 0.025 at layer 8, 0.096 at 16, 0.144 at 24, 0.206 at 31). (4) Layer benchmark (`records/bench_layer_cost.json`, run before this file was written): a cached call with 132 query rows 39.9 ms, a dense call (690 rows) 80.7 ms, partial from layer 11 with all cached rows 67.5 ms, from layer 24 50.2 ms, prompt+written rows only from layer 11 48.0 ms and from layer 0 52.2 ms, blank rows only from layer 11 56.0 ms. An earlier estimate of mine (partial from layer 11 about 55 ms) was wrong: weights are read in every layer whatever the row count.

**Stage A (k = 1: every non-dense call is partial; asks only "does this refresh restore the answers", speed secondary).** Cells: P1-l0-context (the realizable version of B-stale: prompt + written rows recomputed from layer 0 in the call), P1-l11-context, P1-l11-all, P1-l24-all, P1-l11-blank. Readouts: correct answers, net vs in-process D:C-0.9 (dense solves 68 in the earlier process) with 95% bootstrap over questions (10,000, seed 23) and lost/gained, paired difference vs S32:main, speed vs D:C-0.9 and S32:main (ratio of mean latency, bootstrap over questions), calls, partial calls, and the cost-model time predicted from the logged per-layer rows.

**Predictions (point [80% range]; mine, before decode).** S32:main net -9 [-14, -4] (parity with stage 1 is checked on tokens, 164/164). Net vs D:C-0.9: P1-l0-context -3 [-10, +3]; P1-l11-context -4 [-11, +3]; P1-l11-all -2 [-8, +4]; P1-l24-all -5 [-12, +2]; P1-l11-blank -6 [-13, +1]. P(P1-l11-all net >= -3) = 60%; P(P1-l0-context net >= -3) = 50%; P(P1-l11-context net >= -3) = 45%. Speed vs D:C-0.9 from the benchmark costs and S32:main's call pattern (53 calls, 7.4 dense): S32:main 2.2x; P1-l0-context 1.8x; P1-l11-context 1.9x; P1-l11-all 1.4x; P1-l24-all 1.85x; P1-l11-blank 1.7x (each +-0.15, speed differences under about 5% are not resolved). Call counts may move by a few percent because a different trajectory is decoded.

**Decision rules (stated before data).** A cell RESTORES if its net vs D:C-0.9 is >= -3 and its paired gain over S32:main is >= +4 (called resolved only if the interval of the gain excludes 0). With 164 tasks (68 dense-correct) the design resolves about +-6 answers, so no cell can be called equal to dense, only "not resolved from dense". Stage B (defined after stage A, only for cells that restore): schedules k in {2, 4} for the cheapest restoring (row class, l0) setting, together with the in-process dense-refresh comparison cells (`dense,k` = a dense call every k-th call, k in {2, 4}). A schedule cell is a speed win only if it restores AND its measured speed exceeds the in-process dense-k cell of the same k by more than the unresolved 5% band. If no stage-A cell restores, stop and report that no tested row class or layer depth fixes it.

**Parity and guards.** S32:main must equal the stage-1 S32:C-0.9 tokens on the first 3 questions (abort otherwise). Unit tests: partial_every_k = 1 with partial_layer = 0 and join = all equals the every-call dense decode on the toy model; default off leaves tokens, call kinds and row counts unchanged (`tests/test_selective_cache.py`, 441 tests pass). On GPU, bf16 GEMMs over different row subsets may flip near-ties, so token equality between a partial cell and a dense cell is reported, not required.

**Not claimed.** Nothing here tests learned gates or per-call choices; the cells are fixed schedules. A restoring cell does not show why it restores (missing vs outdated context, layer vs row-class effect are confounded across cells). Speeds are one timed repeat on one GPU model; on a GPU with more memory bandwidth the fixed per-call cost is smaller and the row-dependent share larger, so these speed ratios do not transfer.

**GPU budget.** Stage A: 7 arms (2 references + 5 cells) x 164 questions x about 3.5 s = about 1.1 h plus 3 min model load.

## Stage C: refresh triggered by the number of words written (defined 2026-11-10, before any stage-C decode; independent of the stage-B outcome, which is not yet analysed)
**Idea (from the discussion).** Staleness is caused by the words that were written after the cached rows were computed, so a refresh should be paid for by that change and not by elapsed calls. New default-off option `SelectiveConfig.refresh_every_words = W` (+ `words_refresh` in {dense, partial}): in addition to the block-start dense calls, refresh once at least W words have been written since the last refresh (the refreshing call's own writes count toward the next one). `dense` = a dense call; `partial` = a partial refresh with `partial_layer` / `partial_join` (here later-block blank rows from layer 11, the stage-A cell that restored the answers at the lowest cost). Unit tests (441 + 2 new): W = 1 equals the every-call dense decode, W = infinity equals the block schedule, dense-call count is monotone in W, a triggered call happens only after >= W words, partial W = 1 from layer 0 equals dense.
**Words per call, measured on the stored HumanEval runs** (answer length up to the first EOS over calls): 4.2 (dense C-0.9), 4.15 (S32:main), 4.9 (dense every 2nd call), 4.9 (every 4th). So "every 2nd call" is about 9-10 words and "every 4th call" about 19-20 words; my earlier "3.4 words per call" was a rough guess and was wrong. Matched thresholds: W = 10 (about K2) and W = 20 (about K4).
**Cells** (HumanEval 0-163, 512, C-0.9, S32 cache; one process, in-process references D:C-0.9 and S32:main): W10-dense, W20-dense, W10-blank11, W20-blank11, and the calls-based comparison cells K2, K4 (a dense refresh every 2nd / 4th call) in the same process.
**Predictions (point [80%]).** Net vs dense: W10-dense -1 [-8, +6], W20-dense -2 [-9, +5], W10-blank11 0 [-7, +6], W20-blank11 -2 [-9, +5], K2 -1 [-8, +6], K4 0 [-8, +8]. Dense (or partial) refresh calls per question: W10 22 [15, 30], W20 13 [9, 17]; K2 about 28 and K4 about 17 as before. Speed vs D:C-0.9 (+-0.2): W10-dense 1.7x, W20-dense 2.05x, W10-blank11 1.95x, W20-blank11 2.15x, K2 1.6x, K4 1.95x. P(a word-count cell beats its matched calls-based cell by >= +4 answers at equal or higher speed) = 25%.
**Decision rules.** Matched pair: W10 with K2 and W20 with K4 if their refresh-call counts are within 15% of each other; otherwise compare on the frontier (net against speed) and say so. A word-count cell is called BETTER than its matched calls cell only if the paired difference in correct answers is >= +4 with an interval excluding 0 at speed not more than 5% lower, or the speed is more than 5% higher at a paired difference of >= -2. Anything else is "not separated from the calls-based schedule" (expected: the design resolves about +-6 answers). A cell RESTORES under the stage-A rule (net >= -3 and paired gain over S32:main >= +4).
**Not claimed.** Exploration on one benchmark; a positive result needs a held-out code set. Counting words may track the damage no better than counting calls. No measured-signal trigger (attention exposure) is tested here.

## Stage D: the best refresh cells on MATH at 512 and 1024 tokens (defined 2026-11-10, before any MATH decode of these cells)
**Why.** (1) The setting "later-block blank rows from layer 11" was chosen after stage A on the same 164 HumanEval tasks: MATH is data it was not tuned on. (2) A refresh costs more at long generations (dense call 152 ms against 44-52 ms cached at 1024 tokens, earlier result), so the cheaper partial refresh should gain more there. (3) On HumanEval the loss of plain S32 was not concentrated in long answers (post hoc split by dense answer length, stage B: net -4 / -4 / -1 for short / middle / long). Limit: plain S32 lost nothing visible on MATH (earlier: net 0 [-7, +7] at 512, within +-1 at 1024), so MATH can show speed and "no harm", NOT recovery.
**Sets and cells** (word lock C-0.9, S32 cache, block 32, EOS truncation, one process per set, arms rotated, warm-up on question 0, in-process references): `math108` = 54 level-5 + 54 level-1-4 MATH questions at 512 tokens (dense C-0.9 solved 31 in an earlier process); `math54half` = every other question of those = 27 + 27 at 1024 tokens (dense solved 18). Arms: D:C-0.9 (dense), S32:main, K4 (dense refresh every 4th call), W20-dense (dense call once 20 words were written since the last refresh), P4-l11-blank (later-block blank rows rejoin at layer 11, every 4th call), W20-blank11 (the same refresh after 20 words written). Words per call on MATH are about 2.3 (answers about 400 tokens over about 180 calls), so W20 is about every 9th call, not every 4th. Scoring is MATH answer matching in-process (no code sandbox). Parity: S32:main must equal the earlier stage-1/2 S32:C-0.9 tokens on the first 3 questions of each set.
**Predictions (point [80% range]; mine, before decode).** Net vs dense: every cell within +-3 of dense, S32:main 0 [-6, +6] at 512 and 0 [-4, +4] at 1024; no cell resolved below dense. Speed vs D:C-0.9 at 512: S32:main 2.1x, K4 1.6x, W20-dense 1.8x, P4-l11-blank 1.9x, W20-blank11 2.0x (+-0.2; from the call counts of the earlier S32 cells, 179 calls with 14 dense, and the measured call costs). At 1024: S32:main 3.1x, K4 2.0x, W20-dense 2.4x, P4-l11-blank 2.6x, W20-blank11 2.9x (+-0.4; no layer-resolved cost was measured at 1140 rows, so these are rougher). P(P4-l11-blank is more than 5% faster than K4 at both lengths with paired answers >= -2) = 75%; P(the speed ratio P4-l11-blank / K4 is larger at 1024 than at 512) = 65%.
**Decision rules.** NO HARM SEEN: net vs dense >= -3 and the interval of the paired difference against S32:main not clearly negative (the design resolves about +-6 at 108 and +-4 at 54 questions; it cannot call anything equal). SPEED WIN of a blank-row cell over the dense-refresh cell of its trigger (P4-l11-blank vs K4; W20-blank11 vs W20-dense): speed more than 5% higher (ratio of mean latency, bootstrap over questions, same process) at a paired accuracy difference >= -2. LONG-GENERATION CLAIM: the ratio (P4-l11-blank speed / K4 speed) at 1024 against at 512, with a bootstrap interval; called larger only if the two intervals do not overlap.
**Not claimed.** Recovery (nothing to recover on MATH); generalisation to code (HumanEval is still the only code set; the repo has no MBPP data or scorer); anything about layers other than 11; speed on other hardware. One timed repeat per cell; speed intervals under about 5% are not resolved.

## Stage E: the blank-row refresh stacked with the learned context word lock, against the other strategies (defined 2026-11-10, before any stage-E decode; stage D at 1024 tokens still running)
**Decision taken.** Keep as the representation strategy "P4" = later-block blank rows rejoin at layer 11 every 4th call after the dense call that opens each block (S32 cache underneath). The word-count triggers are dropped (W20-blank11 was -4 on HumanEval and -4 on MATH 512, both unresolved, with 13 partial calls per question on MATH against 34 for P4).
**Question.** Does P4 keep its answers and speed when the word lock is the learned context rule Lctx-0.8 (the MATH-fitted HistGradientBoosting rule, sha256-checked, never refit; its lambda is a precision target) instead of the confidence threshold C-0.9, and where does each combination sit on the speed-answers frontier? Word lock and representation cache are crossed: cache in {D (dense, no cache), S32 (block-start dense call only), K4 (dense refresh every 4th call), P4}, word lock in {C-0.9, C-0.8, Lctx-0.8}.
**Arms (10, one process per set, rotated, warm-up on question 0):** D:C-0.9 (the reference), D:Lctx-0.8, S32:C-0.9, S32:C-0.8, S32:Lctx-0.8, K4:C-0.9, K4:Lctx-0.8, P4:C-0.9, P4:C-0.8, P4:Lctx-0.8. C-0.8 is the matched-precision confidence comparator (Lctx-0.8's target precision equals C-0.8's pooled precision). Sets: HumanEval 0-163 (512 tokens; scoring deferred, rescored in the bwrap sandbox) and MATH 108 (54 level-5 + 54 level-1-4, 512 tokens; scored in-process). Parity: every S32 arm must equal the stage-1 tokens of the same arm on the first 3 questions (abort otherwise); P4:C-0.9 should reproduce stage B's P4-l11-blank answers on HumanEval (69; decoding is deterministic).
**Known from earlier stages (not predictions):** HumanEval dense C-0.9 68; stage-1 nets S32:C-0.9 -9, S32:C-0.8 -5, S32:Lctx-0.8 -11, D:Lctx-0.8 -2 (speed 1.30x); MATH dense 31, S32:C-0.9 0, S32:C-0.8 -1, S32:Lctx-0.8 -5 (2.68x). The Lctx rule leaves a stray closing-code-fence line in 5 of 164 HumanEval answers when dense (6 under S32); that is a word-lock formatting effect, it lowers Lctx's HumanEval score in every cell, and stripped-fence rescoring is NOT part of this stage.
**Predictions (point [80% range]; mine).** HumanEval net vs dense C-0.9: K4:C-0.9 0, K4:Lctx-0.8 -4 [-11, +3], P4:C-0.9 +1 (identical to stage B), P4:C-0.8 -2 [-9, +5], P4:Lctx-0.8 -5 [-12, +2]; speed vs D:C-0.9: D:Lctx-0.8 1.3x, S32:C-0.9 2.3x, S32:C-0.8 2.6x, S32:Lctx-0.8 2.85x, K4:C-0.9 2.0x, K4:Lctx-0.8 2.5x, P4:C-0.9 2.2x, P4:C-0.8 2.5x, P4:Lctx-0.8 2.7x (+-0.2). MATH net: D:Lctx-0.8 -3 [-10, +4], K4:Lctx-0.8 -2 [-9, +5], P4:C-0.9 +2, P4:C-0.8 0 [-7, +7], P4:Lctx-0.8 -3 [-10, +4]; speed: D:Lctx-0.8 1.25x, S32:C-0.8 2.45x, S32:Lctx-0.8 2.7x, K4:Lctx-0.8 2.1x, P4:C-0.9 2.1x, P4:C-0.8 2.4x, P4:Lctx-0.8 2.6x (+-0.25). P(P4 recovers at least 4 of the 11 answers S32:Lctx-0.8 loses on HumanEval) = 45%.
**Decision rules.** STACK KEEPS ITS ADVANTAGE on a set if P4:Lctx-0.8 is more than 5% faster than P4:C-0.8 (same process) at a paired accuracy difference >= -3. P4 RECOVERS the Lctx loss if the paired gain P4:Lctx-0.8 minus S32:Lctx-0.8 is >= +4 on HumanEval. FRONTIER: per set, an arm is on the frontier if no other arm is faster with at least as many correct answers; RECOMMENDED CELL = the arm with the highest minimum speed over the two sets among arms with net vs dense >= -3 on MATH and >= -5 on HumanEval (resolution about +-6, so this is "no loss seen", not equality).
