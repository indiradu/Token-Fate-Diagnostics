# Pre-registration: cross-line consistency audit of the quality damage on HumanEval (analysis 7)

Written 2026-11-08 BEFORE any set was built, any divergence/signature statistic was computed, or any program was read for this audit. CPU only, pure Python (stdlib), threads 1, no GPU. Data: `results/farcache_stack_20261105/records/{stage1,diag_he}.jsonl` (HumanEval 0-163, gen 512, block 32, LLaDA-8B-Instruct, temperature 0; stored `text`, `tokens` (512 gen positions, `first_eos` marks the end), `correct`, `scoring_status`) and `manifests/he164.jsonl` (prompt `question`, tests). Scores are the stored `correct` field; nothing is re-executed (re-running tests on the pool programs would unblind the labelling).

## Words (per the repo's terminology rule)
WORD LOCK = which blank positions get a token written per call (C-0.9, C-0.8 confidence thresholds; Lctx-0.8 learned context rule). REPRESENTATION CACHE = which rows' K/V are reused from the last dense refresh (S32 = query blanks are the 32-block's blanks, S16 = next 16 blanks; dense refresh at each block start; D = dense, no cache). Rows concerned: blank rows outside the query set (and prompt/older written rows) in the cache cells; the audited object is the generated answer program (answer rows), dataset HumanEval.

## Question
The collaborator read 4 of the 17 programs lost by S32:C-0.9 by eye (HumanEval/4: a line sums a list and the return sums it again; /9: a loop reads the last item of an empty list; /16: drops `.lower()`) and proposes that cache-induced failures are local slips or *disagreements between lines written against different views of the context*. That reading is 4 programs, read by someone who knew they were lost. Test it with pre-specified automatic measures and a blind labelling.

## Cells and sets
Reference: D:C-0.9 (68/164 correct). Main cache cells: S32:C-0.9, S32:C-0.8, S32:Lctx-0.8, S16:C-0.9, S16:C-0.8. S16:Lctx-0.8 (broken-code transfer failure) is excluded from every main contrast and reported separately (counts, parse rate, divergence, signatures only). Dense word-lock controls (churn that is NOT due to the cache): D:C-0.8 and D:Lctx-0.8 against D:C-0.9.
Per cell vs the reference, per task: LOST (ref `correct`, cell not), GAINED (ref not, cell correct), CHANGED-SAME-PASS / CHANGED-SAME-FAIL (both pass / both fail, `text` differs after `.strip()`), IDENTICAL (`text` equal after strip). A cell's program is "TEXT-ONLY changed" if its text differs but the normalized code (below) is equal.
Sensitivity (pre-registered): the word-lock-matched comparison (S32:C-0.8 and S16:C-0.8 vs D:C-0.8; S32:Lctx-0.8 vs D:Lctx-0.8) and the word-lock-clean comparison (only S32:C-0.9, S16:C-0.9, which share the reference word lock).
Also pre-registered: tasks HumanEval/4, /9, /16 generated the hypothesis. Every primary test is reported with and without them (the collaborator's fourth program is unidentified; it is not excluded and that is a stated limit).

## Automatic analysis (fixed before computing)
Extraction: last ```python fence (the regex of `src/regret_remasking/code_eval.extract_python_code`, copied, falling back to the raw text). Normalized code: parse; drop blank lines, comment-only lines and docstring lines (via ast line ranges; if the code does not parse keep raw non-blank non-comment lines); trailing whitespace stripped.
**First divergence.** Token level: first gen position d where the cell tokens differ from the reference tokens (compared up to the shorter of the two first_eos, +1; if one is a prefix of the other, d = the shorter length). Reported: d, d / reference length (first_eos), block = d // 32, offset in block = d % 32 binned [0,8) [8,16) [16,24) [24,32) (an offset-0 bin means the first quarter of a block just after the dense refresh). Caveat fixed now: the call at which each token was written is not stored, so offset in block is only a proxy for staleness.
**Edit class** (difflib SequenceMatcher on normalized lines, cell vs reference): TEXT-ONLY (normalized equal); LOCAL (exactly 1 non-equal hunk and at most 2 lines on each side); BLOCK (exactly 1 hunk, 3+ lines on either side); STRUCTURAL (2 or more hunks separated by at least one equal line). Unparsable = reported as its own class. The "different algorithm" judgement is left to the human labelling, not the automatic rule.
**Static signatures** (ast, exactly these 6, applied to every cell's program for all 164 tasks, reported for every set and for pass/fail strata, regardless of whether they separate):
 S1 undefined name: a Load name that is never bound in the module (not builtin, import, arg, def, class, assignment/for/with/except/comprehension target).
 S2 unused local: a name assigned in a function (not `_`-prefixed) and never loaded in that function.
 S3 recompute-after-assign: in one function, `v = E` where E is a Call (or a BinOp with >= 5 AST nodes) containing a non-constant, and a later (by line) identical E (same ast.dump) occurs elsewhere in the function with no rebinding of v or of any name in E between the two lines.
 S4 unguarded index of a possibly-empty sequence: subscript x[0] or x[-1] (x a Name), where x is bound to an empty literal ([] , '', "", list()) in the same function or tested for emptiness (`not x`, `x == []`, `len(x) == 0`, `len(x) > 0`, bare `if x`) in it, and the subscript is not enclosed by an If/IfExp/While/BoolOp whose test mentions x.
 S5 unreachable code: a statement following return/raise/break/continue in the same block.
 S6 implicit-None path: the entry-point function (or any function containing `return <expr>`) whose last top-level statement is not return/raise/while-True/try-with-return, i.e. it can fall off the end after some path returns a value.
 S0 (status, not a signature): does not parse.
Each signature is reported as the share of programs having it, and as "new vs reference" (present in the cell program, absent in the reference program of the same task).
**Per-task.** Number of cache cells (of the 5 main) losing each dense-passing task; compared to a null where each cell loses its observed count of tasks uniformly at random among the 68 dense-passing tasks (10,000 draws, seed 20261108): expected and observed tasks lost by >= 2, >= 3, >= 4 cells. This tests concentration (heterogeneous tasks) not mechanism.
**Dense churn control.** Loss rates among the 68 dense-pass tasks (exact Clopper-Pearson) for D:C-0.8, D:Lctx-0.8 vs the five cache cells; the "excess" = cache LOST minus dense-control LOST (counts only).

## Blind labelling
Unit. A pool item is a pair (task, program X to label, sibling program Y) with an opaque id. X is the program whose failure is being characterised:
 CL  = cache-LOST: X = the cache cell's program, Y = D:C-0.9 program.
 DL  = dense-control-LOST: X = D:C-0.8 / D:Lctx-0.8 program, Y = D:C-0.9 program.
 CGd = dense counterpart of cache-GAINED: X = the D:C-0.9 (wrong) program on a task some main cache cell gained, Y = that cache cell's (passing) program.
 DGd = dense counterpart of dense-control-GAINED: X = D:C-0.9 (wrong) program, Y = the dense-control cell's program.
 CSP, CSF = cache CHANGED-SAME-PASS / -FAIL: X = cache cell's program, Y = D:C-0.9 program.
 DSP, DSF = dense-control CHANGED-SAME-PASS / -FAIL (same).
A pool item can belong to several classes (same text produced by several cells / same task); it is labelled once and counted in each class. Duplicate (task, X text) pairs are one item. The labeller never sees class, cell, or pass/fail; it sees the HumanEval prompt, X and Y in random left/right position as "Program 1 (label this)" and "Program 2 (sibling)" (lines identical to the prompt header are elided in both). Items shown in shuffled order; opaque ids are random hex; the key (`pool_key.json`) is written by `build_pool.py`, is not printed, and is not opened until both labelling passes are saved.
Caps, sampling (seed 20261108, `random.Random`): CL <= 32 (first ALL unique items from S32:C-0.9 and S32:Lctx-0.8; then fill from S32:C-0.8, S16:C-0.9, S16:C-0.8 by seeded sampling; if the mandatory part exceeds 32 keep all of it); DL: all (<= 11); CGd <= 10 and DGd <= 8 (seeded samples of unique tasks); CSP <= 6, CSF <= 8, DSP <= 4, DSF <= 4 (seeded). Total about 80.
Categories (X is characterised, using the task spec and Y; judged by reading, not executing; assign ONE; precedence by decision order below):
 (e) other: unparsable, truncated, degenerate/repetitive, or I cannot decide.
 (d) correct but different: I find no defect in X for the full spec including the edge cases the docstring implies.
 (b) cross-line inconsistency: the defect is a RELATION between two or more lines/segments of X. Isolation test: each of the lines, judged alone against the signature and docstring, is plausible, and the program is wrong only because they disagree (an intermediate value computed and then recomputed/contradicted or double counted, an index or state assumed by one line that another line contradicts, an initialisation or loop bound that does not fit the indexing used later, a returned value not the one built above). Either line could be edited to fix it.
 (a) local slip: one line/expression/token is wrong against the spec taken alone (isolation test fails for that one line) and the other lines of X are consistent with the correct version (single-locus repair makes X correct without any other line changing).
 (c) wrong algorithm / misread spec: X is internally coherent but implements something else, or needs two or more coordinated line changes to be correct, and the lines do not conflict with one another.
 Decision order: (e) -> (d) -> (b) if the isolation test is satisfied for a conflicting pair -> (a) if a single line is wrong in isolation -> (c). Each label also gets a confidence H/L and a one-line note naming the line(s). Pass 1 labels all items. Pass 2 re-labels the same pool in a different random order with pass-1 labels not consulted (the labeller is the same agent and keeps memory of pass 1 within the session: it is NOT an independent rater, and agreement is only an upper bound on reliability). Reported: raw agreement, Cohen's kappa (5 categories, and b vs not-b), and the share of (b) under the pass-1, pass-2 labels and under "agreed in both passes only". Primary analysis uses pass 1 (fixed now); pass 2 and agreed-only are robustness.
 Built-in validity check (reported): among items whose class is known to pass (CSP, and Y of GAINED) the share I labelled (d) vs among failing X; i.e. how well blind reading detects real defects.

## Unblinding and tests (fixed now)
Primary question: is the share of (b) among failing programs higher in CL than (i) in DL (dense word-lock control failures) and (ii) in CGd (what the dense decoder got wrong on tasks the cache cell fixed)? Shares with exact (Clopper-Pearson 95%) intervals; one-sided Fisher exact test of CL > DL and CL > CGd; permutation test (10,000, seed 20261108) of the difference in shares as a cross-check; each reported with the actual n. Also pooled baseline DL + CGd + DGd (all "dense-version-wrong" programs). Sensitivities: without tasks 4, 9, 16; one item per task per class (first in the cell order S32:C-0.9, S32:Lctx-0.8, S32:C-0.8, S16:C-0.9, S16:C-0.8); C-0.9 cells only; high-confidence labels only; pass-2 labels; "(a)+(b) vs (c)" grouping. CSF (cache fail->fail) is shown as a further reference.
Decision rule (fixed): SUPPORTED if the (b) share in CL is >= 0.40 AND both one-sided Fisher p <= 0.05 (vs DL and vs CGd) in the primary analysis; WEAKLY SUPPORTED if the (b) share in CL is >= 0.30 and exceeds both baseline shares by >= 10 percentage points but the p-criterion fails; NOT SUPPORTED if the CL (b) share is < 0.25 or is not above at least one of the two baselines; otherwise UNRESOLVED. If the (b) label is common in all failing classes (including dense), the finding is "cross-line inconsistency is how code errors of this decoder look, not a cache signature".
Secondary: (1) position of first divergence in the answer and the offset in the 32-block (CL vs all changed programs and vs dense-control changes); (2) edit class distribution CL vs DL vs CGd; (3) signatures per set; (4) per-task multiplicity vs null; (5) dense churn control. (6) Share of CL lost programs whose first divergence is within the first quarter after a block start vs the share expected from all changed cells (Fisher).

## What this audit cannot show (fixed now)
- It is post hoc and exploratory: n is of order 15-35 per class, one labeller (a model that was told the hypothesis; it is not blind to the hypothesis, only to class), with intervals wider than +-20 points.
- "Lines written against different views of the context" is a statement about the decode schedule (which call wrote which token and which cached view it saw). The records store no write times, so the mechanism is not testable here; a cross-line inconsistency label is consistent with it but equally consistent with ordinary decoder errors.
- Lost-vs-gained conditions differ in selection (regression to the mean on borderline tasks), so (b)-share differences between LOST and GAINED-counterpart classes need not reflect the cache.

## Addendum 1 (2026-11-08, before building the pool; edits made after an adequacy review of this protocol, still before any set was built or any program read)
- Order of operations (binding): (1) `build_pool.py` computes the sets internally and prints ONLY class counts, no task ids; (2) both labelling passes are done on the stripped pool; (3) only then `analyze_audit.py` (divergence, edit class, signatures, per-task multiplicity) and unblinding. No automatic statistic by task is printed before the two passes are saved. `pool_key.json` is not opened before `labels/pass1.jsonl` and `labels/pass2.jsonl` both exist.
- Leaks already present in the labeller's context (stated, not removed): (i) `diag_he_results.md` was read and names 11 tasks lost by >= 4 cells (HumanEval/16, 43, 25, 9, 105, 158, 47, 12, 128, 49, 82); (ii) the hypothesis text names HumanEval/4, /9, /16; (iii) the endings of the 9 stage-1 programs of HumanEval/1 were glimpsed (`return groups` vs `return result`; HumanEval/1 is a plain task, not named as lost). The "without hypothesis-generating tasks" sensitivity therefore excludes the union of {4, 9, 16} and the 11 tasks above (13 tasks), not only {4, 9, 16}.
- Pool items shown to the labeller carry no task index, cell, class, first_eos or token counts (the prompt itself of course identifies the task; this cannot be removed).
- CL composition changed: cap 38 (was 32); all unique items from S32:C-0.9 and S32:Lctx-0.8 first; then at least 6 unique items from S16:C-0.9 (or all if fewer) so the "C-0.9 cells only" sensitivity has two cells; then fill from S32:C-0.8 and S16:C-0.8 by seeded sampling. If the mandatory part exceeds the cap it is kept whole. Other caps lowered to keep the pool near 80: CSP <= 4, CSF <= 6, DSP <= 3, DSF <= 3 (CGd <= 10, DGd <= 8, DL all).
- The detectors S1-S6 are unit-tested on synthetic snippets only, not on the HumanEval/4, /9, /16 programs.
- Token comparison: up to min(first_eos_a, first_eos_b) + 1, `first_eos is None` taken as 512. Source: `stage1.jsonl` rows with `set == "he164"`.
- Labelling is chunked (about 8-10 items per read; labels appended per chunk to `labels/pass1.jsonl` / `labels/pass2.jsonl` as {id, cat, conf, note}); pass 2 uses a different seeded order.

## Addendum 2 (2026-11-08, written after both labelling passes were saved and BEFORE `pool_key.json` was opened or any automatic statistic was computed)
What happened during labelling that the protocol did not anticipate (all recorded here, none derived from outcome data):
- Pool built: 77 items (CL 38, DL 10, CGd 10, DGd 8, CSP 4, CSF 6, DSP 3, DSF 3; an item may carry several class tags). Program 1 (to label) is always shown first and Program 2 (sibling) second; the "random left/right position" in the main text was dropped to keep the labelled program unambiguous.
- Stray fence. Several programs end with a lone closing "```" line (no opening fence), or begin with an unclosed "```python" line. The repo's scorer fallback (`code_eval.extract_python_code`) then keeps that fence line, which is a SyntaxError, so such programs fail regardless of their logic. I noticed this at item 49 of pass 1 and relabelled the one earlier item that had it (id 3fcdef: d -> e; the pass-1 file records the correction in its note, made before any unblinding). Rule used throughout: a program whose extracted code does not parse (stray fence, `import doctestmod()` and similar syntax errors) is category (e), as pre-registered. Because (e) items are a formatting/syntax artefact and not a logic error, the primary (b)-share analysis is also reported with (e) items removed from the denominator ("logic errors only"); the pre-registered denominator (all failing items) stays the headline.
- Added descriptive measure F (not pre-registered, added during labelling): share of programs whose extracted code has a stray fence line (computed by the same extraction as the scorer), per cell and per set; it is part of S0 (unparsable) and is reported separately so it can be read as "fence artefact" vs "other syntax".
- Added coding convention for (b): the note starts with a subtype tag (b-undef undefined/unbound name, b-type value type conflict between lines, b-index index-convention conflict, b-empty index of an empty-initialised sequence, b-dup variable overwritten or recomputed, b-dead variable never updated or dead guard, b-init initialisation conflicts with later use, b-logic other control-flow conflict). Within one line a type mismatch is (a), across different lines (b); the (b) category is therefore broad and includes mechanical slips such as an undefined loop variable. A "strict (b)" sensitivity (b-dup, b-dead, b-logic, b-init, b-empty only: structural disagreements about what a variable holds) is reported next to the broad one; it is fixed here before unblinding.
- Reliability caveat unchanged: pass 2 was done by the same agent in the same session, so memory of pass 1 was not erased (I recognised many items); the agreement rate is an upper bound.
- The labeller knows the HumanEval canonical solutions from memory for many tasks; (d) labels (correct) can be checked against the stored `correct` flag (validity table).

- Correction (made before unblinding): the union of {4, 9, 16} and the 11 tasks named in `diag_he_results.md` is 12 tasks, not 13 (9 and 16 appear in both). The sensitivity excludes those 12.
