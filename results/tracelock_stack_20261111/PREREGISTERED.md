# Does our blank-row refresh compose with TraceLock, a second published learned word lock, and does TraceLock beat a confidence threshold at the same number of calls? (written 2026-11-11, before any GPU decode of this directory)

**Words.** WORD LOCK = which blanks are written in a call (saves calls). REPRESENTATION CACHE = which rows' K/V are reused (saves compute per call). Row types: prompt rows, written rows (answer positions holding a token), blank rows (answer positions still MASK). **TraceLock** = the published learned controller (`paper_trace.PaperTraceController` over `HiddenProjector`; frozen, `results/locking_paper_redesign_20260920_161812/e2_train/full/attempt_01/best_controller.pt` sha a36a47e8..., projector sha 6cba72b5...; trained at gen 128 on mixed GSM8K / KodCode / NQ / Alpaca teacher traces): a blank is written iff its score is strictly above 0.95, else only the best-scoring blank; it reads the layer-30/31/32 hidden states of EVERY row of the prefix (prompt + answer rows up to the window end) of the CURRENT call. Cells: **S32** (compute only the current 32-block's blank rows plus the rows written on the previous call; a dense call opens each block), **K4** (plus a dense call every 4th call), **P4** (plus a partial refresh of the later-block blank rows from layer 11 every 4th call). The engine (`selective_cache.py`, `lock="trace"`, default off) keeps each row's projected TraceLock features in a per-position store: rows the cache computes get fresh features, rows it does not compute (prompt rows, older written rows) keep the features of the call that last computed them. Feasibility, the three mismatches (window vs block, stale features, length) and the parity plan: `FEASIBILITY.md`.

**Datasets.** Evaluation: MATH 108 (54 level-5 + 54 level-1-4 of MATH-500) and HumanEval 164 at 512 tokens, block 32, LLaDA-8B-Instruct bf16, argmax, RTX 5000 Ada; and the earlier 124-case panel (HumanEval 0-69 + the same 54 MATH level-5) at 256 tokens. Threshold selection: 40 questions (the first 20 GSM8K-train and 20 KodCode of the earlier E2 selection split, `manifests/selection40.jsonl`; disjoint from MATH-500 and HumanEval by construction, different distribution from both).

**Questions.**
- Q1 (composition). With TraceLock as the word lock, does each cache cell (S32, K4, P4) keep the accuracy of its dense block-geometry twin `DB:TraceLock` while being faster? Does P4 beat K4 (the rule of the other stages: more than 5% faster at paired answers >= -2)?
- Q2 (learned vs threshold). Does TraceLock beat a confidence threshold that makes the same number of calls? (earlier answer on the 124 panel at 256 tokens: no, 43/124 against 45/124 for C-adaptive-0.9567 and 45/124 for B0.)
- Q3 (cost). What does the controller cost: FLOPs (projector + controller, with the convention below), time per call, memory.

## Design
Arms are `<cache>:<word lock>`; one process per set, arms rotated per question, one unrecorded warm-up per arm on the first question, one timed repeat, in-process reference D:C-0.9.
| arm | what it is |
|---|---|
| D:C-0.9 | dense decoder, 32-blocks, confidence 0.9 (the reference of every stage) |
| D:TraceLock | dense decoder, TraceLock as published: moving window [first blank, first blank + 32) (`paper_decode` T-adaptive) |
| **DB:TraceLock** | dense decoder, TraceLock over the fixed 32-block (`paper_decode` T-block, NEW, 4-line edit): the dense twin of the cached cells. Added to the requested list because the cached cells are block-shaped; without it a cache effect cannot be told from the window-to-block change |
| D:C-matched | dense, 32-blocks, confidence threshold c* chosen so that its mean calls equal DB:TraceLock's on the selection questions |
| S32 / K4 / P4 : TraceLock | the engine, `lock="trace"`, first-EOS truncation on (as in every other stage; the dense decoders have none) |
| S32 / P4 : C-matched | the engine, `lock="conf"` at c* |
256-token cell: D:C-0.9, D:C-adaptive (the earlier E2 anchor: confidence 0.956667, moving window), D:TraceLock, DB:TraceLock, S32/K4/P4:TraceLock, S32/P4:C-0.9567. c* is NOT re-selected at 256; the E2 threshold (selected at 256 in the moving window) is used as is.

**Matched threshold (stage SEL, the E2 procedure re-run at 512 and block geometry).** Target = mean calls of DB:TraceLock on the 40 selection questions (the moving-window D:TraceLock's mean calls on the same questions is recorded, not used). Dense C-block thresholds on {0.80, 0.85, 0.90, 0.93, 0.95, 0.97}, extended upward {0.98, 0.99, 0.995} while the target exceeds the largest mean and downward {0.7, 0.6, 0.5} while it is below the smallest, then 4 interior points between the two bracketing thresholds; c* = the evaluated threshold whose mean calls is nearest to the target (`trace_lock.pick_threshold`, tested). Written to `records/selection.json` before any evaluation decode. Sanity: if the target is outside the evaluated range (`unmatched_*`) or DB:TraceLock averages fewer than 20 calls (controller collapse) the match is reported as unusable and every "equal calls" claim is withdrawn; if the selection stage fails, C-0.8 is used and labelled a fallback.

**Length.** The controller was trained at 128 tokens and validated at 256; 512 is 4x beyond its training length (absolute sinusoidal positions, prefix up to 4x longer). I run 512 because every other stage, the in-process references and MATH level-5 need it, and add the 256-token cell (the length of the earlier validation) with the same TraceLock arms. Conditional (R4): if D:TraceLock loses more than 12 answers against D:C-0.9 on HumanEval 164 or more than 8 on MATH 108 at 512, the 512 grid is declared uninformative about composition (a controller failure, not a cache result) and the 256-token cell is the primary evidence for Q1 and Q2.

**Parity gate (abort).** Before any evaluation decode: the engine in dense mode (`refresh="every_call"`, `shape="block"`, no truncation, `lock="trace"`) against `DB:TraceLock` (HF forward, `output_hidden_states`) on HumanEval 0-2: tokens, calls and per-call writes must be identical; otherwise the job exits with code 3 and writes `records/parity.json` (first divergent call, the engine's scores there, min |score - 0.95|). Tolerance, stated in advance: at most one of the three questions may diverge, and only at a call where some engine score is within 2e-3 of 0.95 (float noise at the threshold); any other mismatch aborts. Unit tests on a 32-layer toy (hidden-state convention of LLaDA, checked against `modeling_llada.py`: `hidden_states[i]` is the input of block i, the last is the final-normalised output) pin the same equality and the stale-feature store (`tests/test_trace_lock.py`). Informational (never aborts): D:C-0.9 reproduces the earlier stage-E tokens; at 256, D:TraceLock and D:C-adaptive reproduce the earlier E2 tokens.

**Readouts.** Per arm and set: correct answers; net vs D:C-0.9 with a 95% bootstrap over questions (10,000, seed 23) and lost/gained; the paired comparisons of `analyze_trace_cells.py` (geometry, cache effect vs DB:TraceLock, P4 vs K4, P4 vs S32, TraceLock vs matched confidence); speed = ratio of summed latency (same process); calls, dense/partial calls, fallback calls; controller time per call (projector + controller, synchronised, inside latency); peak GPU memory (`torch.cuda.max_memory_allocated`, reset before each decode); backbone TFLOPs (convention of `scripts/locking_flop_accounting.py`: attention 4dT, projections 4d(d + d_kv), gated MLP 6 d d_ff per computed row and layer, actual per-layer rows, LM head excluded) plus controller TFLOPs (projector per PROJECTED row, i.e. computed rows below the prefix end, + controller input, transformer and heads on the prefix; `controller_flops` with its projector term replaced). Pooled MATH 108 + HumanEval 164 at 512 for the primary rules. HumanEval is scored afterwards (`rescore_trace_records.py`, bwrap on PATH).

## Predictions (point [80% range]; mine, before any decode; earlier numbers: HumanEval 164 D:C-0.9 68 correct, 53.8 calls, 5.2 s; MATH 108 31 correct, 162.7 calls, 16.0 s; S32:C-0.9 HumanEval -9 [-19, +1], K4 0, P4 +1)
*Selection (40 questions, 512 tokens):* DB:TraceLock mean calls 75 [45, 130]; window D:TraceLock 70 [42, 125]; c* 0.957 [0.93, 0.985]; P(unmatched or collapsed) = 10%.
*Calls at 512:* D:TraceLock HumanEval 62 [45, 100], MATH 185 [130, 280]; DB:TraceLock +6% [0%, +20%] over D:TraceLock; D:C-matched within 5% of DB:TraceLock's calls on a set with probability 55%; S32/K4/P4:TraceLock calls vs DB:TraceLock 1.00 [0.85, 1.25].
*Accuracy, net vs D:C-0.9, HumanEval 164 / MATH 108:* D:TraceLock -3 [-12, +4] / -2 [-7, +4]; DB:TraceLock minus D:TraceLock -1 [-6, +4] / 0 [-5, +5]; D:C-matched -1 [-6, +4] / 0 [-4, +4].
*Cache effect, paired against DB:TraceLock (HumanEval / MATH):* S32 -6 [-16, +2] / -2 [-8, +4]; K4 -2 [-10, +6] / -1 [-7, +5]; P4 -3 [-11, +5] / -1 [-7, +5]. P4 minus K4: -2 [-9, +5] / -1 [-6, +4]; P4 minus S32: +3 [-3, +9] / +1 [-4, +6].
*Mechanism stated in advance:* P4's refresh touches only later-block blank rows' K/V, which are NOT in the controller's prefix (prompt + rows below the block end), so under TraceLock P4 has exactly S32's stale prefix features; only K4's dense call every 4th call de-stales them. Hence I expect P4's gain over S32 to be smaller under TraceLock than under C-0.9 (+10 on HumanEval there) and K4 to be relatively better than in the C-0.9 stage.
*TraceLock vs matched confidence at equal calls, paired (HumanEval / MATH):* dense DB:TraceLock minus D:C-matched -2 [-9, +5] / -1 [-6, +4]; S32 -3 [-10, +4] / -2 [-7, +4]; P4 -3 [-10, +4] / -1 [-6, +4]. P(TraceLock beats the matched threshold by >= +4 on the pooled 272, dense) = 10%.
*Speed, vs D:C-0.9 (HumanEval / MATH):* D:TraceLock 0.80x [0.55, 1.1] / 0.85x [0.55, 1.2] (more calls and about 5 ms of controller per dense call); S32:TraceLock 1.65x [1.2, 2.2] / 1.85x [1.4, 2.5]; K4 1.3x [1.0, 1.7] / 1.55x [1.2, 2.0]; P4 1.6x [1.2, 2.1] / 1.8x [1.4, 2.4]. Speed of S32 over DB:TraceLock 2.1x [1.6, 2.8]; P4 over K4 1.25x [1.08, 1.45].
*Controller cost:* 4.5 ms per call [2.5, 9] under S32/P4 (launch-bound; projector + 3-layer transformer on a prefix of 200-700 rows), 5.5 ms [3, 11] on dense calls; its share of latency 9% [4, 18] under S32; controller TFLOPs about 0.6% [0.3, 2] of the backbone TFLOPs under S32 and 0.2% [0.1, 0.6] dense, so the FLOP overhead is negligible and the time overhead is not.
*Memory (peak allocated GiB, weights are 15):* dense arms 15.9 [15.4, 17.5]; engine arms 16.6 [16.0, 18.5]; TraceLock adds under 0.15 above the same engine cell with a confidence lock.
*256-token cell (124 panel):* D:TraceLock equals the earlier E2 T-adaptive tokens on >= 120 of 124 questions with probability 70% (calls 80 [70, 90]); D:TraceLock net vs D:C-0.9 -2 [-8, +4]; DB:TraceLock minus D:TraceLock 0 [-6, +6]; S32 / K4 / P4 minus DB:TraceLock -4 [-11, +3] / -2 [-9, +5] / -3 [-10, +4].
*Probabilities:* P(R4 triggers, 512 declared uninformative) = 12%; P(R1 holds) = 42% on HumanEval, 50% on MATH, 45% pooled (the speed half holds with about 90%, the accuracy half with about 50%); P(P4 composes, R2) = 55% pooled, S32 40%, K4 60%; P(TraceLock beats the matched threshold, R3, dense, pooled) = 10%.
*Wall time:* job 8 h [6, 11] (parity 10 min, selection 70 min [45, 120], MATH 108 3.6 h, 256 cell 0.8 h, HumanEval 164 1.9 h, plus five model loads); limit 12 h.

## Decision rules (stated before data; resolution about +-6 answers at these sizes, so "holds" means no loss / gain seen at the stated value, not equality; a result is called RESOLVED only if the 95% interval of the paired difference excludes 0)
- **R1 (P4 beats K4 under TraceLock).** Speed of P4:TraceLock over K4:TraceLock > 1.05 AND paired P4 - K4 >= -2, on a set and pooled.
- **R2 (a cell composes with TraceLock).** Paired cell minus DB:TraceLock >= -4 AND speed over DB:TraceLock > 1.3, pooled MATH 108 + HumanEval 164 at 512 (per set reported as well). "Does not compose" otherwise; "resolved" only with the interval.
- **R3 (TraceLock beats the matched confidence threshold).** Primary: DB:TraceLock minus D:C-matched >= +4 pooled with the calls ratio inside +-5% (otherwise "no verdict: not at equal calls"). The cached pairs (S32, P4) are secondary: their calls are not matched by construction (c* is chosen dense), so they are read at their realised calls ratio. At 256 the same rule against the E2 threshold. No evidence for the learned controller beyond a confidence threshold is the default reading.
- **R4 (length sentinel).** D:TraceLock net vs D:C-0.9 <= -12 on HumanEval 164 or <= -8 on MATH 108 at 512 -> the 512 composition grid is uninformative, 256 is primary. Any other value: the cached cells are read against DB:TraceLock as in R2.
- **R5 (cost).** Reported, not decided: controller ms per call and share of latency; controller TFLOPs as a share of backbone TFLOPs; peak memory against the same engine cell with a confidence lock.

## Not claimed
(1) The engine's stale-feature store is a choice (features of the last call that computed a row), not the published method, which always had fresh states; a cache loss under TraceLock can be a loss of the controller's inputs, not of K/V, and this run cannot separate the two (a stage with fresh features for uncomputed rows would; proposed, not run). (2) S32/K4/P4 use 32-blocks and first-EOS truncation; D:TraceLock uses the published moving window and no truncation, so D:TraceLock vs the cached cells mixes cache, geometry and truncation; the read against DB:TraceLock mixes cache and truncation only. (3) One controller (the E2 checkpoint, not the later aligned-collab retrain), one cutoff (0.95), no retraining or recalibration under the cache or at 512. (4) c* is selected on GSM8K/KodCode questions, evaluated on MATH/HumanEval; calls can differ from the target on the evaluation sets, and the cached cells are not call-matched. (5) One timed repeat; speed intervals under about 5% are not resolved; the controller time includes a device synchronisation that other arms do not have (it is inside latency_s for TraceLock arms). (6) The earlier "no evidence for the learned controller" was at 256 tokens in the moving window on 124 cases; this run extends it to 512, 32-blocks and the caches but does not retest the learned controller against a better learned one. (7) HumanEval correctness is deferred to a rescoring step; no HumanEval accuracy exists until `rescore_trace_records.py` has run.

## Amendment 1 (2026-11-11, before job 290336 started and before any decode; changes no decision rule, no prediction, no abort rule)
1. **Diagnostic added to the parity stage.** For each of the 3 parity questions `records/parity.json` now also holds `call0_diagnostic`: one HF forward (`output_hidden_states=True`) and one fresh engine forward from the identical first-call input, the largest absolute differences of `hidden_states[30], [31], [32]` and of the TraceLock scores of the first block's 32 blanks, and min |score - 0.95|. It is wrapped so that it can never abort the job. Purpose: if the gate fails, a max score difference far below the distance of any score to the cutoff points to float noise at the threshold, a large one to a logic bug. The abort rule (identical tokens, calls and writes, with the single near-threshold tolerance above) is unchanged. Tested on the CPU toy only (differences 0 there).
2. **Why not 128 tokens (note, not a rule change).** The controller was trained at 128 tokens (teacher decode, block 4, one token per step). I do not run 128: MATH level-5 answers do not fit in 128 tokens, so the dense reference itself would be truncated, and the only deployed evidence for this checkpoint is the earlier 256-token 124-case panel. The 256-token cell is therefore the "closer to the training length" fallback by precedent (the length of the earlier validation), not by training geometry; 512 is 4x and 256 is 2x the training length.
3. **Prompt identity for the informational E2 parity (checked).** The prompts the E2 evaluation manifests resolve to (`_resolve_prompt`) are identical to those of `manifests/he164.jsonl` (70/70 HumanEval 0-69) and `manifests/math_l5.jsonl` (54/54), so the prediction "D:TraceLock equals the earlier E2 T-adaptive tokens on >= 120 of 124 questions" is not void for a prompt-format reason; it still depends on bit-level reproducibility across nodes and library versions.
