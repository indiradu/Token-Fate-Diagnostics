# Can the published learned word lock TraceLock run under our representation caches? Feasibility (written 2026-11-11, before any code change and before any decode)

**Words.** WORD LOCK = which blanks are written in a call (saves calls). REPRESENTATION CACHE = which rows' K/V are reused (saves compute per call). Row types: prompt rows, written rows (answer positions that hold a token), blank rows (answer positions still MASK). Cells: S32 (compute only the current 32-block's blank rows plus the rows written on the previous call; a dense call opens each block), K4 (plus a dense call every 4th call), P4 (plus a partial refresh of the later-block blank rows from layer 11 every 4th call).

## Verdict: FEASIBLE, with three disclosed mismatches. Build and queue. (Built the same day: see PREREGISTERED.md, orchestration/, tests/test_trace_lock.py.)

## What TraceLock reads at decode time (from `paper_decode.py` lines 507-530 and `paper_trace.py`; checked, not assumed)
- Controller: `PaperTraceController` (3-layer pre-norm transformer encoder, d=384, 8 heads, ff 768, 4096 sinusoidal absolute positions, a learned threshold token), cutoff 0.95. Checkpoint `results/locking_paper_redesign_20260920_161812/e2_train/full/attempt_01/best_controller.pt` (sha256 a36a47e8...2f93c8, val F0.5 0.8299), projector `.../projector/projector.pt` (sha256 6cba72b5...55d). Frozen; these are the ones behind the earlier 43/124 result (`surelock_token_vs_tracelock_20260922_2145/policies.json`). Loading: `PaperTraceController.load(path, device)`, `HiddenProjector.load(path, device)`, fp32. (The later `aligned_collab` retrained controller is a different checkpoint and is NOT used.)
- Inputs per call: for EVERY row of positions [0, right) (prompt rows + all answer rows up to `right`, written and blank alike) the hidden states `hidden_states[30]`, `[31]`, `[32]` of the CURRENT forward = the input of block 31, the input of block 32 and the final-normalised output (LLaDA appends `x` before each block, then `ln_f(x)` last). Per row the projector makes 832 features (3 state autoencoders + 2 delta autoencoders, rounded through fp16); there is NO time history: a call's score uses only that call's hidden states. The controller then attends over all `right` rows bidirectionally (all-ones validity mask; so there IS prefix attention over the prompt) and emits one logit per row minus a learned threshold logit; sigmoid > 0.95 writes the blank (else the single best blank is written).
- `right` = first blank + 32 (a moving window; arm `T-adaptive` is in `WINDOW_ARMS`). Eligible blanks = blanks in [first, right).
- Training: teacher decode (one token per step, gen 128, block 4), mixed GSM8K / KodCode / NQ / Alpaca data, frames cropped at random ends (25% to 100% of the answer), dense fresh hidden states; validation window 32. Earlier evaluation: 256 tokens (HumanEval 70 + MATH L5 54), where it matched dense B0 within 2 answers.

## (a) What the engine needs (all default-off; `lock="trace"`)
1. **Hidden-state exposure from `SelectiveEngine.forward`.** The engine already runs every layer by hand. With `cfg.trace` set, keep `x` entering layers L-2 and L-1 (= `hidden_states[30]`, `[31]`) and `ln_f(x_final)` (= `[32]`) for ALL computed rows (not only the decoding window; `head_rows="window"` only restricts the vocabulary head), returned in `info["hid"]` with the row positions. Cost: three (computed rows x 4096) bf16 tensors per call and one extra RMS/LayerNorm; nothing else changes.
2. **Per-position history buffer.** A `(T, 832)` fp16 feature store plus a validity flag, owned by a new small module `trace_lock.py` (`TraceScorer`). The projector is row-wise, so each call projects only the computed rows with position < `right` and overwrites their features; rows the cache does not recompute keep the features of the last call that computed them (prompt rows and older written rows: the block-opening dense call; in-block written rows: the call after their write). Storing the projected features instead of raw hidden states is exact (the projector is a pure row function) and 5x smaller. A validity check raises if the controller input would contain a row that was never computed (only possible with `refresh="none"`, which is rejected).
3. **`lock="trace"` branch** in `_lock_write` (score, `> cfg.threshold` writes, best-blank fallback, same `_argmax_stable` as `paper_decode`) and a controller call site in `decode_selective`. `right` = end of the current 32-block (shape "block" only), `position_ids = arange(right)`.
4. **Controller loading**: in the runner (`PaperTraceController.load`, `HiddenProjector.load`, sha256 check), not in the engine.
5. Also needed outside the engine: a block-geometry dense twin in `paper_decode.py` (arm `T-block`, four-line edit: same controller path, `right` = block end instead of first blank + 32), because the engine's S32 shape is a fixed 32-block and the published `T-adaptive` is a moving window (see mismatch 1).

## (b) Does the training geometry match what the cached engine gives? Three mismatches
1. **Window versus block.** Published TraceLock decides over a moving window [first blank, first blank + 32); the S32/K4/P4 cells decide over the fixed 32-block (fewer eligible blanks late in a block; the controller's prefix is the block end rather than first blank + 32). The controller never sees a window/block flag, only a prefix of different length, and its training crops were random ends, so this is inside its training distribution, but it is a different word lock operating point: fewer parallel writes near block ends, so more calls. This changes the word lock, not only the cache. Control: the dense block-geometry twin `T-block` (arm `DB:TraceLock`) isolates the cache effect from the geometry effect; the published window decoder is kept as `D:TraceLock`.
2. **Stale features for rows the cache does not recompute.** Training saw fresh hidden states for every row. Under S32/K4/P4 prompt rows and older written rows feed the controller with features from the block-opening call (stale by up to one block's worth of calls; in our own measurements a written row moves a median 3% per call in this feature space and a blank 8%, so a block's worth of staleness is a modest but not zero shift). The blank rows themselves are recomputed every call (with stale K/V of the context rows, exactly as for the confidence lock). Risk: a systematic bias of the scores of blanks that attend to the stale prefix features; can show up as over- or under-writing relative to the dense block twin. Not measured offline; the paired S32/K4/P4 versus `DB:TraceLock` comparison is the test. Compare the learned `Lctx` word lock: it failed under the 16-blank window (HumanEval net -28) because its inputs were defined on the 32-block geometry (label-level precision 0.924 against a 0.993 target); under the 32-block cache it was already calibrated (precision within 0.0004 of target). TraceLock has no block-position input, so that specific route (a feature defined on a geometry that changes) is absent, but mismatch 1 is the analogue and mismatch 2 is new.
3. **Length.** The controller was trained at gen 128 and validated at 256. The cells here use 512 (the length of every other stage, and MATH level-5 needs it), so positions up to prompt + 512 are 4x beyond the training range of the absolute sinusoidal encoding and the prefix is up to 4x longer. This can degrade the controller independently of any cache. Control: `DB:TraceLock` / `D:TraceLock` against `D:C-0.9` at 512 measure this directly, and the earlier 124-case panel (HumanEval 0-69 + MATH level-5 54) is run at 256 (the length of the earlier validation) with the TraceLock arms and the earlier E2 threshold (0.956667) as the confidence comparison; a pre-registered rule (R4) makes that cell primary if D:TraceLock degrades at 512.

Other differences that stay (and are named): first-EOS truncation is on in the engine cells (as in every other stage) and off in the dense decoder, which changes calls slightly (53.2 vs 53.8 calls for C-0.9 on HumanEval earlier); sampling is argmax (temperature 0) everywhere.

## (c) Parity plan
- Unit tests on the toy model (a 32-layer toy so that `hidden_states` has the 33 LLaDA entries; random projector and controller; a cutoff chosen so that both multi-write and fallback calls occur): the engine with `refresh="every_call"`, `shape="block"`, `eos_truncation=False`, `lock="trace"` must reproduce `decode_paper_policy(arm="T-block")` tokens, call count, and per-call writes; the hidden-state exposure must equal `output_hidden_states` of the toy; the feature store must equal the dense projector output in dense mode and must keep stale features for non-computed rows in S32 mode; row counts per layer must be unchanged by the trace option; the default (trace off) paths must remain token-identical (existing 472 tests).
- GPU smoke inside the Slurm job, before the main run: 3 real questions (HumanEval 0-2): `S32D:TraceLock` (engine dense) against `DB:TraceLock` (paper_decode T-block) with truncation off, tokens up to the first EOS and call counts must be identical on all 3, else the job aborts cleanly with a message. A 2-question smoke of every arm runs first. Dense-engine versus HF-forward hidden states are bit-compatible in the earlier C-0.9 parity (S32D = dense C-block), so I expect exact parity; a score within 1e-3 of 0.95 can still flip a write, which is the one way a 3/3 gate could fail without a bug (stated in the pre-registration).
- The window decoder `T-adaptive` is NOT reproduced by the engine (the engine's "window" shape is the next 32 blanks, not the next 32 positions) and is not claimed to be.

## (d) Cost
- Controller FLOPs (conventions of `scripts/locking_flop_accounting.py`): projector about 31 MFLOP per projected row; controller about 3.6 GFLOP at a 400-row prefix (+ 0.26 GFLOP input projection). Dense call at T=700: about 16 GFLOP of controller against about 10 TFLOP of backbone (0.16%); under S32 (about 40 computed rows, about 0.5 TFLOP) about 5 GFLOP (1%). So the FLOP overhead is negligible; the wall-clock overhead is kernel-launch bound (a few ms per call for projector + controller, against about 40 ms per S32 call on HumanEval): expect a 5-15% time overhead, recorded per call (`rule_time_s`).
- Memory: feature store 800 x 832 x 2 B = 1.3 MB; hidden exposure a few tens of MB; controller + projector 66 MB.
- GPU time: about 9 arms x (164 HumanEval + 108 MATH) questions at 512, about 45 s and about 115 s per question across all arms, plus a 40-question selection pass (about 70 min: 2 TraceLock decodes + about 10 dense confidence thresholds per question) and the 124-case panel at 256 (about 50 min): about 8 h on one RTX 5000 Ada (6-11 h), requested with a 12 h limit.

## Not ill-defined
Every input of the controller exists in the engine (computed rows give fresh last-layer hidden states, others give stored ones). The one thing that is not a like-for-like of the published method is the stale feature rows; it is named as a mismatch and tested through paired controls, not assumed away.
