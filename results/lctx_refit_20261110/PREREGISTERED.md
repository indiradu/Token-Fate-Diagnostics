# Does refitting the learned context word lock Lctx in the geometry of use fix its 16-window transfer failure, and does fitting under the cache change it under the 32-block cache? (written 2026-11-10, before any GPU decode of this directory)

**Words.** WORD LOCK = which blanks are written in a call. REPRESENTATION CACHE = which rows' K/V are reused. **Lctx-0.8** = the MATH-fitted HistGradientBoosting word lock of `results/longlen_wordlock_20261103/rules/math512/Lctx_c0.8.pkl` (200 rounds, lr 0.1, `early_stopping=False`, seed 23; six inputs: confidence, entropy, margin, dist_written, local_mask_ratio, pos_in_block; label = the proposal at that call equals the final token; fitted on 448,003 rows of 60 MATH level-5 one-word-per-call traces at 512 tokens in 32-blocks with fresh, dense representations; lambda = 0.9605 chosen on 20 other questions so that the pooled precision of everything the rule admits equals that of the confidence threshold C-0.8 on the same rows, 0.99486; the "0.8" is a precision target, not a confidence cutoff). **S16** = Elastic-Cache's shape: query blanks are the next 16 blanks, dense call at every block start (ours). **S32c / P4** = 32-block shape, representation cache with a dense call at every block start and our blank-row partial refresh every 4th call from layer 11 (`partial_every_k=4, partial_layer=11, partial_join="blank"`). All datasets are named: collection on MATH level-5 (the 60 + 20 questions of the original rule), evaluation on HumanEval 164 and MATH 108 (54 level-5 + 54 level-1-4), 512 tokens, LLaDA-8B-Instruct bf16, block 32, temperature 0.

**Question.** (Q1) The original Lctx-0.8 fails under S16 (HumanEval 164: net -28 [-39, -17] against dense C-0.9, only 63% of outputs parse on tasks 0-99; MATH 108: -11 [-19, -3]). If that is a transfer failure of the rule (its inputs are defined on the 32-block geometry and the 16-window changes the candidate set), then the same rule fitted on one-word-per-call traces collected **in the S16 geometry** should fix it. (Q2) The original rule was fitted on dense representations; under a representation cache the confidences come partly from stored K/V. Does a rule fitted on traces collected **under the S32 cache with the blank-row refresh** (R-S32c) behave differently from the original under the same cache (P4)?

**What is built (all default-off; the original rule and its files are never written).**
- `SelectiveConfig.collect_rows` (+ `SelectiveResult.collected`): per call and per eligible blank, the six inputs from the SAME function the rule uses at decode time (`context_rules.block_features` plus the window `pos_in_block` override, factored into `_rule_features`, now used by `lock="rule"` too) and the proposal. Unit tests (`tests/test_lctx_refit.py`): default-off leaves tokens, call counts, refresh kinds and writes unchanged in both shapes; the logged features are bit-equal to what a recording rule receives on the same trajectory; labels are filled after the decode from the final tokens. Full suite 451 passed, 2 skipped (443 + 8).
- Collection geometries (one word per call: `lock="topk", topk=1`, the original fit's B0 convention): **R-S16** = shape window (16 blanks), dense call at every block start (`refresh="block"`); **R-S32c** = shape block, S32 cache with the blank-row refresh every 4th call from layer 11. **eos_truncation: OFF in both.** I checked: the original fit is the repo's dense B0 baseline (`paper_decode` arm "B0"), which has no first-EOS truncation (stage F also calls D:Naive "dense B0, no truncation" and treats the truncated version as a separate twin). So the collection matches the original fit, and the evaluation arms (which use truncation, as in every earlier stage) differ from it in that one respect; the effect is confined to blocks that contain or follow the first EOS and to pos_in_block there (the truncated block has fewer blanks, which the rule also sees through `pos_in_block`). This is a disclosed mismatch, not tested.
- Questions: the same 60 fit and 20 threshold questions as the original rule (`rules.json`, text from `data/math500_level5.jsonl`, `manifests/fit_thr.jsonl`), interleaved 3 fit : 1 threshold. Disjointness from MATH 108 and HumanEval 164 by id, normalised text and 200-character substring: `validation/disjoint.json` (checked 2026-11-10: disjoint).
- Fit (CPU, `orchestration/fit_refit.py`, run at the end of the collection job): the estimator is `sklearn.base.clone` of the original pickle's estimator with seed 23. **Row filter (primary): every logged row whose proposal is not EOS/EOT**, including the first call of each block. The original fit additionally dropped the first call of each block (`step_in_block >= 1`; recorded in `fit_feature_ranges.json`). I keep these rows because the rule is applied to them at decode time (15-21% of calls); a secondary fit with the original filter is computed and reported but not saved or decoded. First call of a block := the call on which the 32-block of the leftmost blank has nothing written yet (`n_first_block == 32`). **Pooled precision, exactly as reconstructed from the original**: target = mean label over ALL threshold-question rows (non-EOS/EOT) with confidence >= 0.8, pooled over the 20 questions, not averaged per question; lambda = the lowest score threshold at which the mean label over all admitted threshold rows is still >= target (ties never split). The original fitter (`analyze_context.py` / `ctxlib.py`) no longer exists in the repository (its worktree is gone), so this is a **reconstruction** pinned by the surviving evidence (the original pickle's hyperparameters, `rules.json`: every `precision_on_threshold_set` is >= its target by under 1e-4; the earlier session's written description); it cannot be shown to reproduce the original pickle. The "C-0.8" confidence used for the target is the mask-suppressed float32 proposal confidence that `block_features` logs; at decode time S16:C-0.8 uses Elastic's float64 `min(threshold, max)` rule (stage-1 convention), which differs only in rounding and in the always-write-the-best-blank guard.
- Outputs: `rules/R-S16/Lctx_refit_S16_c0.8.pkl`, `rules/R-S32c/Lctx_refit_S32c_c0.8.pkl` (+ `rules.json` with sha256, lambda, features, target precision, admitted share, same fields as the original), `validation/fit_feature_ranges_<geom>.json` (original format), `validation/refit_<geom>.{json,md}`: admitted shares, AUROC on the held-out threshold rows (with a cluster bootstrap over questions of AUROC(refit) - AUROC(original)), the original rule's behaviour on the new rows (precision at its own lambda 0.9605, admitted share, AUROC, and its lambda recalibrated to the new target), and the feature-range shift against the original fit rows.

**Stage G (evaluation, decodes after the rules exist).** One process per set, 7 arms, arms rotated per question, one unrecorded warm-up per arm on question 0, in-process reference **D:C-0.9** (dense C-block, which is what "dense C-0.9" means everywhere), one timed repeat, Slurm GPU. Sets: **HumanEval 164** (scoring deferred: this host has no bwrap sandbox; `orchestration/rescore_records.py G_he164` with bubblewrap on PATH afterwards) and **MATH 108** (scored in-process). Arms, all 512 tokens with first-EOS truncation and a dense call at each block start:

| arm | shape | word lock |
|---|---|---|
| D:C-0.9 | dense, 32-blocks | confidence 0.9 |
| S16:C-0.8 | 16-window | Elastic's min(threshold, max) rule at 0.8 |

Parity (abort on a mismatch on any of the first 3 questions of a set): D:C-0.9, S16:C-0.8, S16:Lctx-0.8 equal the farcache_stack stage-1 tokens; P4:C-0.8, P4:Lctx-0.8 equal the depth_refresh stage-E tokens (when those records exist). Decoding is deterministic, so the five reference arms should be token-identical to their earlier records on essentially all questions; their nets below are therefore reproductions, not new information. Readouts per set: correct answers, net vs D:C-0.9 with a 95% bootstrap over questions (10,000, seed 23) and lost/gained, paired differences between arms, speed = ratio of summed decode time in the same process with the same bootstrap, calls, dense/partial calls, fallback share, and on HumanEval the share of outputs whose code part parses (`ast.parse`, the earlier diagnostic's extractor).

**Decision rules (stated before data; resolution about +-6 answers at these sizes, so every "holds" is "no loss seen / gain seen at the point-value threshold", not equality; I name a result resolved only when the 95% interval excludes 0).**
- **R0 (label-level, CPU).** The original rule shows a label-level transfer failure in a geometry if its pooled precision at lambda 0.9605 on that geometry's threshold rows is at least 0.005 below C-0.8's precision there. If R-S16 does NOT show it, the S16 failure is not a one-word-per-call precision failure and a refit is not expected to fix it through calibration; a decode that nevertheless improves would then point to the row filter or the shift between one-word-per-call and multi-write decoding.
- **R1 (speed advantage kept).** The refit rule keeps its speed advantage over C-0.8 of the same shape on a set if its summed decode time is more than 5% lower (same process) at a paired accuracy difference >= -3 against that C-0.8 arm.
- **R2 (S16 failure removed).** `S16:Lctx-refit` net vs D:C-0.9 >= -6 AND (HumanEval only) parse share within 0.05 of D:C-0.9's or higher. Called "removed" only if it holds on both sets; "improved" if the paired gain over S16:Lctx-0.8 is >= +6 on both sets, whatever R2 says.
- **R3 (cache-conditioned refit beats the original).** Paired gain `P4:Lctx-refit` minus `P4:Lctx-0.8` >= +4 on a set; called resolved only if its interval excludes 0.
- **R4 (label-level gain).** AUROC(refit) - AUROC(original) on the held-out threshold rows >= 0.01 with the cluster-bootstrap interval excluding 0, per geometry.

**Not claimed.** (1) The fit is on one-word-per-call traces and the rule is used in multi-write decoding; neither the original nor the refit tests that shift, and a refit that improves precision at the label level need not improve joint multi-write behaviour. (2) The refit differs from the original in geometry AND in the row filter (first call of each block kept) AND in being fitted by a reconstructed pipeline on new traces of the same questions; there is no control "R-D32" (dense 32-block B0 collected and fitted with this pipeline), which would separate pipeline reconstruction from geometry (about 1 GPU-hour; proposed, not run). The `orig_filter` variant only separates the row filter at the label level. (3) The rules are fitted on MATH level-5 only; HumanEval is a transfer in every cell, and a HumanEval gain or loss says nothing about the rule outside MATH. (4) One lambda (the 0.8 precision target) and one seed; no hyperparameter search; the threshold set (20 questions) fixes lambda for both geometries separately. (5) Nothing here says why the S16 failure happens beyond whatever R0 shows; the refit is a test of the transfer hypothesis, not an explanation. (6) Speed is one timed repeat on one GPU model (ratios under about 5% are not resolved); S16 and P4 cells are not compared against each other. (7) The five reference arms are reproductions of earlier stages and are not new evidence. (8) Evaluation questions were never used for fitting or for choosing lambda; the collection geometry choices (blank-row refresh every 4th call from layer 11) were chosen on HumanEval in an earlier stage, as noted there.
