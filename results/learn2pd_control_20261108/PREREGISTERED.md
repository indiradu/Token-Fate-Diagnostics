# Pre-registration: Learn2PD as a word lock against confidence thresholds (C-c) and the learned context rule (Lctx), dense / dense + truncation / selective cache (2026-11-08)

Written BEFORE any test-set decode of this campaign (HumanEval 164 and MATH 108). Already run before this file: CPU unit tests; trace collection and a tau calibration run on TRAINING-split questions only (listed below); a 2-question crash test on training questions (`records/pilot.jsonl`). The first decodes of test questions are the parity checks at the start of the first stage-1 process.

Words. WORD LOCK = which blank positions get a word written in a call (saves calls). REPRESENTATION CACHE (the far-blank / selective cache of `selective_cache_20261104`, S32 shape) = which rows have their K/V cached instead of recomputed (saves compute per call). "Lctx-0.8" is the learned context word lock whose 0.8 is a PRECISION TARGET (cutoff lambda = 0.9605 on a gradient-boosted score), not a confidence cutoff. Row types: prompt rows, written answer rows, blank rows. Datasets: HumanEval 164 (gen 512) and MATH 108 = 54 Level-5 + 54 Level 1-4 of MATH-500 (gen 512). LLaDA-8B-Instruct bf16, temperature 0, block 32, fused SDPA, one timed repeat, threads fixed to 1.

## What Learn2PD is, as implemented (see `OFFICIAL_CODE_NOTES.md`; the official code was READ, not run)
- Filter: Linear(32,32)-ReLU-Linear(32,32), 2,112 parameters; input = the confidence of all 32 slots of the current block (written slots included); a blank is written iff sigmoid(logit) > tau (strict, tau on the SIGMOID, as in the official code); EVERY call also writes the single most confident blank (official code: top-k with k = 1 stays on). The paper's wording ("tau applied to the filter output") is ambiguous; the code is unambiguous.
- Official released weights exist for LLaDA-8B-Instruct, block 32: `llada/layer_2_flan.pth` (sha256 0d375569970208524fd14ce0a71ed3d1c9b51a237c8c397f6601a8ff7adbab5f), trained by the authors on raw (no chat template) FLAN prompts, gen 256; arm `L2PD-off`, tau 0.96.
- Retrained filter (arms `L2PD-pub`, `L2PD-match`): our own EGP traces (labels: the proposal equals the final token of the standard one-word-per-call decode, the Lctx-type label), MATH-train and GSM8K-train questions only (`manifests/train_*.jsonl`, `validation/train_disjoint.json`: exact and substring overlap with every test question is empty), paper recipe (AdamW 1e-3, full batch, BCE over 32 slots, <= 5,000 epochs; the epoch count is chosen on held-out training questions: 5,000 won). 72 fit questions (42 MATH @512 + 30 GSM8K @256, 2,216 EGP rows) and 24 held-out questions (14 MATH Level 1-4 + 10 GSM8K). The paper used 2,640 FLAN questions: our training set is about 30x smaller, in-domain for MATH, none for code (code is a transfer, like Lctx's). Weakness found only after collection: the held-out MATH questions are all Level 1-4 (role = every 4th list index, and the list alternates Level 5 / Level 1-4), so calibration and epoch choice never saw a Level-5 held-out question.
- Differences from the official pipeline that remain: weights (retrained arm), training data and prompts, 30x fewer rows, our confidence convention (float32, mask-suppressed argmax), and truncation: ours is a cut after the first WRITTEN EOS/EOT (all S32 and T cells); the official `L2P+EoT` also cuts at the most confident masked position whose argmax is EOS, which we do not implement. The official dual cache recomputes all 32 block rows each call, and so does our S32 L2PD cell (`block_rows`), so its rows per call are larger than S32:C-c's.
- tau frozen here (`filters/rules.json`): **published 0.96**; **matched 0.946** = the call-count match to C-0.8 on the held-out training MATH questions (dense decodes of 14 questions: C-0.9 129.6, C-0.8 103.2, Lctx-0.8 99.7, official weights @0.96 103.1, retrained @0.90/0.93/0.96/0.98/0.99 = 83.1/93.8/111.2/202.0/356.6 calls; linear interpolation between 0.93 and 0.96). The precision match to C-0.8 (the Lctx rule: lowest tau whose pooled precision on held-out one-word-per-call blank rows reaches that of confidence >= 0.8; 140,448 rows) gave **0.963**, i.e. the published 0.96 is already precision-matched, which is why the second variant is the call-count match instead. Nothing was tuned on any test question.

## Cells (one process per set; speed ratios only inside a process; cell order rotated per question; one warm-up decode per cell)
D (dense word lock, no truncation): C-0.9 (reference everywhere), C-0.8, Lctx-0.8, L2PD-pub, L2PD-match, L2PD-off.
T (dense + first-EOS truncation twin: selective engine, a dense call on every call): C-0.9, L2PD-match.
S32 (selective cache; dense call at every block start; first-EOS truncation): C-0.9, C-0.8, C-0.7, C-0.6, Lctx-0.8, L2PD-pub, L2PD-match.
Cut for budget (reported as not run): dense C-0.7 and C-0.6, twins of Lctx-0.8 and L2PD-pub, S32:L2PD-off. The dense lowered-threshold question is answered in the S32 cells (C-0.7, C-0.6); the dense answer-level comparison uses C-0.8 only.
Parity checks at the start of the first process (4 questions: HumanEval/0, /1, math500-l5-1, -9): D:C-0.9, D:C-0.8, D:Lctx-0.8 token- and call-identical to the far-cache campaign's dense records (`results/farcache_stack_20261105/records/stage1.jsonl`); T:C-0.9, T:Lctx-0.8, T:L2PD-* equal their dense cells up to the first EOS with no more calls. Unit tests (CPU, toy model): `tests/test_l2pd_rule.py` (19 tests: strict sigmoid tau, forced top-1, 32-vector covers written slots in block order, the S32 engine with a dense call every call equals the dense L2PD decode, default-off leaves the other rules unchanged); full suite 413 passed.
Scoring: repo scorers; HumanEval scorer guard (canonical solution must pass, absolute interpreter path, abort on `sandbox_error`).
