# Far-blank cache stacked with three word locks; answer quality on code and easier sets (2026-11-05 to 2026-11-07)

**STATUS: complete.** Nothing committed or pushed; GPU released. Pre-registration: `PREREGISTERED.md` (written before any decode, with an Outcome section appended afterwards). Tables with intervals: `results.md` (all sets), `diag_he_results.md` + `diag_he_pairs.md` (the added HumanEval diagnostics), numbers `summary.json`, records `records/` (generations stay local), frozen decoders `source/` (stages) and `source_diag/` (diagnostics, adds one default-off option), checks `validation/`.

## Words
WORD LOCK = which blank positions get a token written in a call (saves calls): C-0.9 and C-0.8 (confidence thresholds) and Lctx-0.8 (the word-lock agent's learned context rule, MATH-fitted, sha256-checked, never refit). CACHE (the "far-blank cache" of `selective_cache_20261104`) = which rows keep K/V from the last dense refresh instead of being recomputed (saves compute per call). Here: prompt rows, older written rows and blank rows outside the query set are cached; the rows that are computed are the rows written on the previous call plus the query blanks; a dense call (every row) at every block start; first-EOS truncation. **S16** = query blanks are the next 16 blanks (Elastic's shape). **S32** = query blanks are the blanks of the current 32-block (Fast-dLLM dual-cache-like; the word locks are exactly the ones verified earlier). **D** = dense word lock only (no cache). Adaptive trigger and row-selective refresh were dropped. LLaDA-8B-Instruct bf16, temperature 0, block 32, one timed repeat, one process per stage (ratios only within a process).
Datasets: HumanEval 0-163 (gen 512), MATH 108 = 54 L5 + 54 L1-4 (gen 512), GSM8K test 0-199 (gen 256), MATH 54 (even-indexed half: 27 L5 + 27 L1-4; gen 1024). None of these overlaps the Lctx rule's fit/threshold questions (MATH only, 80 questions; `manifests/audit.json`; GSM8K collections in this repo are all train-split). MBPP: no data or scorer in the repo, skipped.

## The answer in plain words
1. **The cache stacks with the word lock on speed.** Against dense C-0.9 (MATH 108, 512 tokens): S16:C-0.9 2.05x [1.96, 2.14], S32:C-0.9 2.06x [1.96, 2.18], C-0.8 2.45-2.51x, Lctx-0.8 2.68x (S32) and 3.03x (S16 transfer). At 1024 tokens (MATH 54) the cache cells are 3.1-4.4x (S32:Lctx-0.8 3.95x [3.60, 4.37]) because a dense call is 152 ms and a cached call 44-52 ms. On HumanEval 2.1-3.0x, on GSM8K at 256 tokens only 1.3-2.0x (short prompts and answers: a call is already cheap and weight-read bound). The word lock and the cache savings multiply almost fully: interaction R 0.95-1.04 in S16; in S32 it falls 4-9% short at 512 (C-0.8 0.947 [0.900, 0.994], Lctx 0.913 [0.856, 0.973]) because the lower-threshold locks need more dense refresh calls (14.3 per question vs 11.4 in S16 at 512).
2. **MATH answers are kept by the C locks; the Lctx rule is the weak point.** Net vs dense C-0.9 (MATH 108, dense 31/108, resolution about +-6): S16:C-0.9 -1 [-8, +6], S32:C-0.9 0 [-7, +7], S16:C-0.8 -2, S32:C-0.8 -1, **S32:Lctx-0.8 -5 [-13, +2]** (not resolved; misses the pre-registered net >= -3 point rule), **S16:Lctx-0.8 -11 [-19, -3]** (resolved loss; it is a transfer: the rule was fitted on 32-blocks and the 16-blank window breaks it). At 1024 (dense 18/54, resolution about +-4) every cell is within +-1 except S16:Lctx -7 [-13, -2]; **S32:Lctx-0.8 is 3.95x at net 0 [-6, +6]**. The best quality-preserving cells: 512: S16:C-0.8 2.51x (net -2), S32:C-0.8 2.45x (-1); 1024: S32:Lctx-0.8 3.95x (0) and S16:C-0.8 3.99x (-1). The primary Lctx claim (S32) is therefore: faster than C-0.8 by about 1.10x at 512 and 1.10x at 1024, answers inside the resolution at 1024, a 5-answer point loss at 512 whose interval includes 0.
3. **Against the permanent freeze (FIX-both, not rerun).** Baseline numbers from `repfreeze_tests_20261029/stack_stage/results.md`: Lctx-0.8+FIX-both 1.775x (512) / 1.683x (1024), C-0.8+FIX-both 1.587x / 1.472x. The cache cells are 2.68x / 3.95x and 2.45x / 3.58x. Part of the gap is an artifact: the old sparse runtime costs about 8.5% before anything is frozen (SPARSE-none 0.914x), and these are different processes; even after crediting FIX-both with that 8.5% (1.94x / 1.84x for the best stack) the cache is clearly ahead, and it does not need the 24% call inflation FIX-both showed at 1024 (here calls rise 8-10% for the C-0.9 cells at 512, 8-9% at 1024).
4. **Staleness shows on code, and on easy MATH only for the Lctx rule.** HumanEval (164 tasks, dense C-0.9 68 correct, resolution about +-6): S16:C-0.9 -6 [-16, +3], S32:C-0.9 -9 [-19, +1], S16:C-0.8 -4, S32:C-0.8 -5, S32:Lctx -11 [-21, -2], S16:Lctx -28 [-39, -17]. On tasks 0-39 (where FIX-both lost 4-5 of 24) the cache loses 3-7 of 24: about the same as FIX-both. The loss is concentrated in tasks 0-99 (dense solves 55 of them): net on tasks 0-99 vs 100-163 is -10 / +1 for S32:C-0.9, -8 / +2 for S16:C-0.9; tasks 100-163 are mostly unsolved by the dense decoder (13 of 64) so there is little to lose there, which is not evidence that the cache is harmless on hard code. On MATH L1-4 (the easier questions) the C cells are within +-1 (512) and Lctx S32 is -3 [-9, +3]; the one resolved L1-4 loss is S16:Lctx (-8 at 512, -6 at 1024).
5. **GSM8K is not a clean "easier set" under this protocol.** Dense C-0.9 gets only 96/200 and 74% of its answers fill the 256-token budget (cut off before `#### answer`), so accuracy is budget-limited. Nets vs dense C-0.9 (resolution about +-8-10 at 200): S16:C-0.9 -13 [-31, +5], S16:C-0.8 -22 [-39, -5], S16:Lctx -26 [-45, -7], S32:C-0.9 -8 [-25, +9], S32:C-0.8 -7 [-24, +10], S32:Lctx +2 [-15, +19]; the dense Lctx cell itself is -7 [-23, +10]. S16 cells are resolved losses on GSM8K (two of three); S32 cells are not resolved. These are short answers where cached rows are a larger share of what the answer rests on, but this run cannot separate that from the budget effect.

## Why code answers drop (added after seeing interim HumanEval; not part of the pre-registration; `diag_he_results.md`)
Process of its own (164 tasks, C-0.9 lock, same-process dense reference 68 correct), one ingredient changed at a time:
- **Lost answers are ordinary wrong code, not truncated or degenerate text.** In the first 100 tasks all 89 lost answers (summed over the six cache cells) are `failed_tests`, median length 170-190 tokens (dense answers 182), longest repeated-token run 2, syntax-valid share 98-99% for the C cells (dense 98%). A typical failure is a plausible slip, e.g. HumanEval/16 drops `.lower()`. Early EOS is not the cause: 7 of 17 lost S32 answers end at least 20 tokens before the dense answer, but EOS truncation alone changes nothing (below). **Exception: S16:Lctx-0.8 writes broken code (63% of outputs parse on tasks 0-99)**; that is the transfer failure, not staleness.
- **EOS truncation is innocent.** S32 with a dense call every call and truncation produces tokens identical to dense C-0.9 on 164/164 tasks (net 0, 1.19x).
- **The window decode is innocent.** S16 with a dense call every call, window 16 and truncation: +1 [-3, +5] (1.12x).
- **The loss comes from the cache of the later blocks' blank rows.** S32 with the block-start refresh and no truncation loses the same 17 tasks as the main cell (17/17 overlap, net -10 [-19, -1]). Caching only prompt and written rows while computing every blank row every call loses nothing (+1 [-8, +10], 1.68x).
- **A more frequent refresh recovers it, at a price.** A dense call every 4th call in addition to each block start: paired +9 [+2, +17] answers over the main cell (net vs dense C-0.9 0 [-9, +9]) at 1.97x instead of 2.24x; every 2nd call: +8 [-1, +17] at 1.58x. These recovered cells are still inside the noise against dense; the paired gain over the main cell is the resolved quantity.
Not tested: refreshing exactly when a token is written (that is every call), refreshing only the first block or the rows near new writes, and a code-specific schedule. What the evidence supports: the cost of the stale far-blank rows is real on code, and a dense call every 4th call recovers it for about 12% of the speed.

## Process notes and limits
- **Restart.** The first stage-1 process died with the session after 100 HumanEval tasks; the partial file is kept (`records/stage1.PARTIAL_killed_session.jsonl`) and was used only for the interim anatomy of lost answers. Stage 1 was rerun from scratch in a single new process, so no speed in this report mixes processes. A stale GPU marker (dead pid) was removed.
- **Parity (validation/parity.json, again all true in the new process).** Dense cells token- and call-identical to the word-lock agent's 512 records (3 MATH questions x 3 locks); S16:C-0.9 token-identical to the selective-cache Part C block+EOS cell; S32:C-0.9 and S32:Lctx-0.8 with a dense call every call equal their dense cells (CPU toy test plus 3 GPU questions). Diagnostic S32:main equals the stage-1 S32:C-0.9 tokens on 164/164 tasks.
- **Kernel.** Dense cells use the standard model path, cache cells the hand-run layers with the same fused SDPA kernel on row subsets (the manual softmax changes tokens and is not used). EOS truncation is part of every cache cell and absent from dense cells; it changes no tokens before the first EOS (shown above).
- **Lctx timing.** Threads fixed to 1; node load median 1.1 (max 1.8 on 12 cores); rule cost 1.56-1.62 ms per call in dense and cache cells alike.
- One timed repeat; speed intervals under about 5% are not resolved; answer resolution +-6 at 108 / HumanEval / GSM8K-ish, +-4 at 54. Per-stratum MATH tables are in `results.md`.
- Dense C-0.9 predictions that were far off: HumanEval 68/164 (predicted 100) and GSM8K 96/200 (predicted 150, budget-limited): see Outcome in `PREREGISTERED.md` for the full list of failed predictions.
