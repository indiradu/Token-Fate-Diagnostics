# Pre-registration: far-blank cache stacked with three word locks, then answer quality on code and easier sets (2026-11-05)

Written BEFORE any GPU decode of this campaign (the CPU tests on toy stacks were run before and say nothing about LLaDA-8B). Parity decodes at the start of the stage-1 process are the first GPU decodes.

Words. WORD LOCK = which blank positions get a token written in a call (saves calls). REPRESENTATION FREEZE / cache = which rows have K/V cached and skipped (saves compute per call). This campaign tests a cache (the FAR-BLANK CACHE of `selective_cache_20261104`: blanks beyond the query set, prompt rows and older written rows keep the K/V of the last dense refresh; dense refresh at every block start; first-EOS truncation) stacked with three word locks. The adaptive trigger and the row-selective refresh are DROPPED (they did not beat the block-start refresh); FIX-both (permanent freeze) is NOT rerun: the baseline is `results/repfreeze_tests_20261029/stack_stage/results.md` (Lctx-0.8+FIX-both 1.775x at 512 MATH 108 / 1.683x at 1024 half; C-0.8+FIX-both 1.587x / 1.472x; FIX-both lost 4-5 of 24 HumanEval 0-39 answers under every lock). Cross-process comparison with those numbers includes an artifact: the old sparse runtime costs about 8.5% before anything is frozen (SPARSE-none 0.914x), the new engine has no such overhead (window-dense 1.02x of dense in Part C).
Models and settings. LLaDA-8B-Instruct bf16, temperature 0, block 32, threshold-style locks.

## Cells (9 per question, one process per stage; speed ratios valid only inside a process)
Dense (word lock only, existing dense decoder `paper_decode`, standard model path, nothing cached): D:C-0.9, D:C-0.8, D:Lctx-0.8.
Cache cells, each lock in two query shapes (all with first-EOS truncation and a dense refresh at every block start, fused SDPA kernel in hand-run layers):
- S16 (Elastic shape): query rows = the next 16 blanks + rows written on the previous call; word lock on those 16 blanks. C-c is Elastic's own rule (Confidence >= c over the window, the best blank if none; float64 softmax), identical to the Part C block+EOS cell for c = 0.9. Lctx in S16 is a TRANSFER: the rule was fitted on block-32 decodes and is applied to the leftmost 16 blanks, with the position-in-block feature taken from the 32-block of the leftmost blank.
- S32 (block-aligned, Fast-dLLM dual-cache-like): query rows = the blanks of the current 32-block + rows written on the previous call; blanks in later blocks, prompt rows and written rows cached. The word locks are exactly `paper_decode`'s C-block rule and X-block rule (Lctx over the block's blanks, the rule file of the word-lock agent, sha256-checked against rules.json, never refit). The primary Lctx claim is in S32.
Differences that remain between a dense cell and its cache cell: the cache itself, first-EOS truncation (dense cells do not truncate), and in S16 the window-16 decode itself. The dense cells use the standard HF model path, the cache cells the hand-run layers with the same fused SDPA kernel on row subsets (Part A/B found that the manual-softmax kernel changes tokens; it is not used here).
Rule time. Lctx's gradient-boosting predict is CPU-load sensitive: all threads fixed to 1 (OMP/MKL/OpenBLAS), node load average recorded at every decode; per-call rule time reported (dense: `scorer_time_s`, cache: features + scoring).

## Sets (disjoint from every Lctx rule fit / threshold question)
- Stage 1 (one process): HumanEval tasks 0-163 at gen 512 (answers short; all 164; the Lctx rules were fitted on MATH only); MATH 108 at gen 512 = `longlen_wordlock` math_l5 (54) + math_l14 (54), verbatim copies, disjoint from the 60 fit + 20 threshold questions (their validation/disjoint.json).
- Stage 2 (one process): GSM8K test questions 0-199 at gen 256 (every GSM8K collection in this repo used the TRAIN split: `manifests/audit.json`; the rules were fitted on MATH), then MATH at gen 1024 on the even-indexed 54-question half (27 L5 + 27 L1-4) of the 108, the same 54 as the earlier 1024 records.
- MBPP: no MBPP data or scorer in the repo; skipped.
Scoring: repo scorers. HumanEval is executed with an absolute interpreter path; a scorer guard (canonical solution must score correct, status must not be `sandbox_error`) aborts the process, and so does any `sandbox_error` record.
One timed repeat per cell. Parity before the stage-1 main run, 3 questions (`validation/parity.json`; the process aborts on a mismatch): dense cells token- and call-identical to the word-lock agent's 512 records (`parity_ref512.json`); S16:C-0.9 token-identical to the Part C block+EOS cell; S32:C-0.9 and S32:Lctx-0.8 with a dense refresh every call and no truncation equal D:C-0.9 / D:Lctx-0.8 (CPU test on a toy model: tests/test_selective_cache.py).

## Readings (per cell, per set; pooled MATH and split L5 / L1-4)
Speed = ratio of summed decode seconds, paired bootstrap over questions, 10,000 resamples. Reported: speed vs D:C-0.9 and vs the cell's own dense lock; interaction R = (cache cell vs D:C-0.9) / [(own dense lock vs D:C-0.9) x (same-shape C-0.9 cache cell vs D:C-0.9)] (R = 1: the lock's and the cache's savings multiply; "multiplicative" if the interval contains 1, "sub-" / "super-multiplicative" if it lies below / above 1); calls per question; ms per call; rows computed per call; dense calls; correct, lost / gained and net vs D:C-0.9 and vs the own dense lock; changed-text share; fills-budget share (first EOS/EOT at position >= gen - 8 or none); median first EOS; Lctx rule ms per call. Resolution: +-6 answers at MATH 108, +-4 at 54, about +-6 at HumanEval 164 and GSM8K 200. A cell is faster/slower only if the speed interval excludes 1; an answer loss or gain is called only if the net interval excludes 0.
Quality-preserving rule (a point rule, as in the earlier campaigns): net vs dense C-0.9 >= -3 on MATH 108; the same proportion (about 2.8% of n) elsewhere: >= -5 on HumanEval 164, >= -6 on GSM8K 200, >= -2 on MATH 54. A cell is "quality-preserving" if it meets the rule; this is not a claim of no loss (intervals are shown). Staleness is read from (a) HumanEval nets (does the cache drop answers on code the way FIX-both did: -4 to -5 of 24 on tasks 0-39; the tasks 0-39 subset is reported separately) and (b) MATH L1-4 per stratum.
