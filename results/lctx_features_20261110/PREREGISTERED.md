# Do extra decode-time features improve the learned context word lock Lctx? Offline ablation first, decodes only behind a pre-registered gate (written 2026-11-10, before any GPU job of this directory and before the engine code that computes the features)

**Words.** WORD LOCK = which blanks are written in a call. REPRESENTATION CACHE = which rows' K/V are reused. **Lctx-0.8** = the MATH-fitted HistGradientBoosting word lock (200 rounds, lr 0.1, `early_stopping=False`, seed 23) on six inputs (confidence, entropy, margin, dist_written, local_mask_ratio, pos_in_block); label = the proposal at that call equals the final token; lambda chosen on 20 threshold questions so the rule's pooled precision equals that of the confidence threshold C-0.8 (the "0.8" is a precision target, not a confidence). **Lctx-X** = the same learner on the six inputs plus extra features (below). **P4** = 32-block shape, representation cache with a dense call at every block start and our blank-row partial refresh every 4th call from layer 11. Datasets: collection and fit on **MATH level-5** (the SAME 60 fit + 20 threshold questions as the original rule and as `results/lctx_refit_20261110`, `manifests/fit_thr.jsonl`, sha256 006af234...), one word per call (`lock="topk", topk=1`), 512 tokens, 32-blocks, representation cache = P4 refresh (this is the refit's R-S32c geometry). Decode evaluation (only behind the gate): **HumanEval 164** and **MATH 108** (54 level-5 + 54 level-1-4), 512 tokens.

**Background (read from `results/lctx_refit_20261110`).** In the R-S32c geometry the six inputs give AUROC 0.9271 against 0.9250 for confidence alone, and at the same pooled precision as C-0.8 (0.9973) admit 34.9% of the threshold rows against 33.7% for C-0.8; in the 16-window geometry 0.9071 against 0.9065. The six inputs add almost nothing to confidence, so a better rule needs new information. This experiment asks whether the cheapest kinds of new information that exist at decode time without extra forward passes provide it.

## Question
(Q1, offline, CPU) Does adding any of four groups of decode-time features to the six inputs raise the AUROC of the proposal-equals-final-token label and the share of blanks admitted at C-0.8's precision, on 20 held-out MATH level-5 questions, by more than the pre-registered gate? (Q2, decodes, only if the gate passes) Does the extended rule keep Lctx's speed advantage over C-0.8 and beat the original six-input rule in answers under the 32-block cache with the blank-row refresh (P4)?

## Features (all computed from the call's own logits, the sequence state at the start of the call and ONE stored copy of the previous call's log-probabilities; no extra forward pass)
Notation: eligible blanks = the blanks the call computes (in the 32-block shape: all blanks of the current block; at the block's first call all 32). W_t = number of words written before call t. `x` = sequence state at the start of the call. The proposal is the mask-suppressed argmax, confidence its probability (as the six inputs). "Previous call" = call t-1; a blank has no previous observation if it was not eligible at t-1 (first call of its block; after a resume).
**Behaviour under multi-write.** Training traces have exactly one word per call, deployment (stage H) writes several. Features are of three kinds: (S) functions of the sequence state at the call, like the original six inputs (distribution shifts only through the state distribution, which the six inputs share); (H) functions of the history, which differ in units when calls write more than one word; for these I use word counts, which coincide with call counts at one word per call; (P) pure per-call quantities. Nothing offline can test the shift between one-word-per-call and multi-write decoding; only stage H can.
- **(a) STABILITY** (history, kind H)
  - `run_words` (words): number of words written since the blank's proposal last changed, = W_t minus W at the call where the current identical-proposal stretch began; 0 when the proposal differs from the previous call's or there is no previous observation. At one word per call equals "number of consecutive previous calls with the identical argmax proposal". Robust version of the spec's runlength (counts words written, not calls).
  - `flip` (0/1/NaN): 1 if the argmax changed since the previous call, 0 if not, NaN if no previous observation.
  - `kl_prev` (nats per written word): KL(p_t || p_{t-1}) of the blank's full-vocabulary distributions, divided by max(1, words written by call t-1); NaN if no previous observation. Equal to the raw KL at one word per call. **The per-word division is an approximation** (KL grows roughly linearly in the number of independent perturbations, not exactly), and refresh calls change distributions by themselves: kl_prev is the feature I expect to shift most between one-word and multi-write decoding. If kl_prev carries the importance in the ablation, that is a warning, not a win.
- **(b) NEIGHBOURS** (state, kind S). Nearest eligible blank on each side (adjacent in the sorted list of eligible blanks; NaN when none, for example the first and last blank of a block, which has no computed neighbour on the outside).
  - `nbr_conf_l`, `nbr_conf_r`: confidence of that blank (NaN when none).
  - `nbr_cand_l`, `nbr_cand_r`: 1 if that blank's confidence >= 0.5 (candidate), else 0, NaN when none. (A tree can derive this from the neighbour confidence; kept because the task asked for it.)
  - `same_l`, `same_r`: 1 if this blank's proposal equals the token at position i-1 / i+1, where that token is the written token if the position is written, the proposal of that blank if it is an eligible blank, NaN if it is a blank that is not computed in this call or outside the sequence.
- **(c) PROPOSAL** (pure per call, kind P)
  - `p_eos`: probability mass on EOS (126081) plus EOT (126348) at this position.
  - `tok_newline`, `tok_space`, `tok_punct` (0/1): class of the proposal token from a table built once from the tokenizer (`assets/token_class.npy`, sha256 in `assets/token_class.json`): newline = the decoded token contains a line break; space = the decoded token begins with whitespace; punct = non-empty after stripping whitespace and made only of characters that are neither letters nor digits. Special tokens and tokens that decode to a partial UTF-8 sequence are 0 in all three. The rank-2 probability is already in `margin` and is not duplicated.
- **(d) FRONTIER** (state, kind S)
  - `dist_leftmost` (positions): position of the blank minus position of the leftmost eligible blank (= the leftmost blank of the block in the block shape).
  - `rank_left` (count): number of eligible blanks to the left of this one.
  - **Dropped: "calls since block start".** In one-word-per-call traces it equals the existing `pos_in_block` x 32 (up to a clamp on the first call), so it is collinear with an input already in the rule; in multi-write decoding a call count would shift. `rank_left` is the new, non-collinear frontier quantity (it differs from `dist_left` whenever written words sit between blanks).
- Missing values are native NaN (HistGradientBoosting handles them; no sentinel). 15 extra features: a 3, b 6, c 4, d 2.

## Offline ablation (CPU, `orchestration/fit_ablation.py`)
Same learner (clone of the original pickle's estimator, 200 rounds, lr 0.1, no early stopping, seed 23), same row filter as the refit's primary fit (every logged row whose proposal is not EOS/EOT, including the first call of each block), same 60 fit / 20 threshold questions, same pooled-precision lambda rule (target = mean label over all threshold rows with confidence >= 0.8; lambda = the lowest score threshold at which the pooled mean label of all admitted threshold rows is still >= target; ties never split). Feature sets (11): `six` (the control: must reproduce the refit's R-S32c numbers), `six+a`, `six+b`, `six+c`, `six+d`, `six+all`, `conf` (confidence alone: AUROC of the raw confidence, admitted share = C-0.8's), `conf+a`, `conf+b`, `conf+c`, `conf+d` (a gradient-boosted model on confidence plus the group; `conf` alone is also fitted as a one-feature GBM so that the conf+group comparisons are like with like).
Per set on the threshold questions: AUROC; admitted share at C-0.8's pooled precision and the achieved precision; cluster bootstrap over the 20 threshold questions, **2,000 resamples (seed 23), resampling questions with replacement and, within each resample, re-choosing the target AND lambda of every set**, so that the interval reflects the whole procedure; the AUROC difference and the admitted-share difference to the six-input control come from the same resamples (paired). Feature importance: permutation importance (drop in AUROC, 3 repeats, seed 23) on the threshold rows for `six+all` and for the best set, per feature and per group (all columns of a group permuted together).
Validity checks written to `validation/`: (V1) the newly collected traces of the first 3 questions are token- and six-input-identical to `results/lctx_refit_20261110/records/traces_S32c` (hard check in the collection job; the remaining questions are compared and reported); (V2) the natively logged `run_words`, `flip`, `nbr_conf_l/r`, `nbr_cand_l/r`, `dist_leftmost`, `rank_left`, `same_l/r` are recomputed post hoc from the logged (call, position, token, confidence) columns and must be equal (this tests the engine's state logic, which toy tests can only spot-check; `kl_prev` and the token-class features cannot be recomputed from the log and are covered by unit tests); (V3) the control reproduces the refit: AUROC within 0.002 of 0.9271 and admitted share within 0.01 of 0.349 (read from `lctx_refit_20261110/validation/refit_S32c.json`).

## Gate (implemented as `orchestration/check_gate.py`; exits 1 on failure; written to disk before any decode)
"Best set" = the one of `six+a`, `six+b`, `six+c`, `six+d`, `six+all` with the largest admitted share at C-0.8's pooled precision (point estimate). The gate passes only if ALL hold: **G0** V3 holds and V2 holds (otherwise the experiment is invalid, not negative). **G1** admitted share of the best set minus admitted share of the six-input control >= 0.05 (5 percentage points). **G2** AUROC difference to the control >= +0.01 AND the lower end of its 95% cluster-bootstrap interval (2.5th percentile of the 2,000 paired resamples) > 0. Only `check_gate.py` decides; stage H does not run otherwise. Selection of the best set among five on the same 20 threshold questions that also fix lambda is optimistic (a winner's-curse bias I do not correct, for lack of a further held-out set): the gate is a screen, the decode is the test. If the gate passes, the extended rule `rules/X/Lctx_X_c0.8.pkl` (+ `rules.json` with sha256, lambda, feature list, token-class table sha256) is written; if it fails, no rule file is written.
A failed gate means: with these 15 features, this learner, 60 fit questions, one-word traces in the R-S32c geometry, no gain large enough to be worth decoding. It does NOT mean that no information beyond confidence exists, nor anything about the multi-write shift.

## Stage H (decode; runs only if the gate passes; the Slurm job runs `check_gate.py` first and exits 0 without decoding if it fails)
One process per set, 4 arms rotated per question, one unrecorded warm-up per arm on question 0, in-process reference **D:C-0.9** (dense C-block), first-EOS truncation, 512 tokens, block 32, one timed repeat. Sets: HumanEval 164 (scoring deferred: this host has no bwrap sandbox; rescore afterwards with the private bubblewrap on PATH) and MATH 108 (scored in-process). Arms: **D:C-0.9**; **P4:C-0.8** (confidence 0.8); **P4:Lctx-0.8** (the original six-input rule, `results/longlen_wordlock_20261103/rules/math512/Lctx_c0.8.pkl`, sha256 checked); **P4:Lctx-X** (extended rule). Parity (abort on a mismatch in the first 3 questions of a set): D:C-0.9, P4:C-0.8, P4:Lctx-0.8 equal their tokens in the earlier stage records (stage 1 / stage E / `lctx_refit` stage G) where those exist.
Readouts: correct answers, net vs D:C-0.9 (95% bootstrap over questions, 10,000, seed 23, lost/gained), paired differences between arms, speed = ratio of summed latency in the same process (same bootstrap), calls, dense/partial calls, fallback share, rule time per call, HumanEval parse share.
**Decision rules (stated before data; resolution about +-6 answers at these sizes, so "holds" means the point-value threshold is met, not that the interval excludes anything; "resolved" only if the 95% interval excludes 0).**
- **H1 (speed advantage kept):** P4:Lctx-X summed decode time more than 5% below P4:C-0.8's (same process) AND paired answer difference vs P4:C-0.8 >= -3, on each set.
- **H2 (beats the six-input rule):** paired P4:Lctx-X minus P4:Lctx-0.8 >= +3 answers on a set; "pooled" = the sum over both sets >= +3; called holding only if it holds on both sets.
- **H3 (overhead):** P4:Lctx-X per-call rule time (features + scoring) minus that of P4:Lctx-0.8 stays under 1.5 ms (a call costs about 30 ms + rows); speed of Lctx-X relative to Lctx-0.8 >= 0.97.

## Predictions (mine, before any data; point [80% range])
**Collection and checks.** Collection 19.5 s per question in the refit (R-S32c): mine 21 s [18, 30] with the feature overhead; 80 questions + smoke + load: 33 min [28, 55]. V1: tokens identical on the first 3 questions 92%; six inputs bit-identical on all 80 questions 80% (if not, the difference is reported, and the control comparison V3 decides validity). V2 holds (exact equality of the natively logged derivable features) 85% on first run (implementation bugs are the risk). V3 holds 90%.
**Ablation, difference to the six-input control (control expected AUROC 0.9271, admitted share 0.349 at precision 0.9973; C-0.8 admits 0.337).**

| set | AUROC difference to `six` | admitted-share difference (points) |
|---|---|---|
| six+a (stability) | +0.004 [0.000, +0.012] | +1.5 [-0.5, +4.5] |
| six+b (neighbours) | +0.002 [-0.001, +0.006] | +0.5 [-0.7, +2.0] |
| six+c (proposal) | +0.001 [-0.001, +0.004] | +0.2 [-0.8, +1.2] |
| six+d (frontier) | 0.000 [-0.001, +0.002] | 0.0 [-0.7, +0.8] |
| six+all | +0.005 [0.000, +0.015] | +2.0 [-0.7, +5.5] |

`conf` as a one-feature GBM: AUROC 0.9250 [0.9245, 0.9255], share 0.340 [0.335, 0.346]. `conf+a` minus `conf`: AUROC +0.005 [+0.001, +0.014]; `conf+b` +0.004 [0, +0.010]; `conf+c` +0.002 [0, +0.005]; `conf+d` +0.002 [0, +0.004] (a position-type feature can explain the small gain of the six inputs over confidence).
My structural reason to expect anything is group (a): "the proposal has not changed for N words" and "the distribution barely moved" are information that a single call's confidence does not contain. The other groups are mostly functions of what confidence and `dist_written` already summarise. **Best set = `six+all` 55%, `six+a` 35%, other 10%.** Top-ranked EXTRA feature by permutation importance in `six+all`: `kl_prev` 45%, `run_words` 25%, `nbr_conf_l` or `nbr_conf_r` 10%, `p_eos` 8%, anything else 12%; group importance ranks (a) first with 70%. `confidence` remains the single most important feature of `six+all` with 85%.
**P(gate passes) = 12%** (G1 is the hard part: +5 points of admitted share is five times what the six inputs add to confidence; G2 is nearly implied by G1). The user's prior is 25%; I am lower because the high-precision region (0.997) leaves little headroom: the admitted set already contains 100x more correct than wrong blanks, and a feature has to push roughly one in seven currently-rejected correct blanks above the line without admitting wrong ones.
**Stage H (conditional on the gate passing, so with probability about 12%).** P4 reference values from earlier stages: HumanEval 164 dense 68; P4:C-0.8 67 (net -1), P4:Lctx-0.8 62 (net -6), speed vs dense 2.74x and 2.92x (Lctx 6.6% faster than C-0.8); MATH 108 dense 31 (P4 values: see the refit's stage G when finished). Mine for P4:Lctx-X: net vs dense -4 [-12, +4] on HumanEval and -3 [-10, +4] on MATH; paired vs P4:Lctx-0.8 +2 [-5, +9] on HumanEval, +2 [-5, +8] on MATH; speed vs P4:C-0.8 1.07x [0.98, 1.16]; fallback and calls per answer within +-8% of P4:Lctx-0.8. P(H1) = 50% on each set; P(H2 on both sets) = 20%, pooled >= +3: 40%; P(H3) = 90% (the extra features cost one [n, vocab] KL and a few gathers per call, 0.3 ms [0.1, 1.5]). Wall time of the decode job (4 arms x 272 questions + smoke): 1.5 h [1.1, 2.2].
**Job times.** Collection + ablation job: 1.4 h [1.0, 2.2] (ablation about 15-45 min on the node's CPUs); limit 3:30. If the gate fails the decode job finishes in about 20 seconds.

## Not claimed
(1) The ablation is label-level: AUROC and admitted share on the proposal-equals-final-token label of one-word-per-call traces; the rule is used in multi-write decoding, and neither the six inputs nor the extra features have a test of that shift offline. (2) Only 20 threshold questions fix lambda, the C-0.8 target and the gate; the bootstrap is over those 20 questions; the selection of the best of five sets is not corrected. (3) One learner (HistGradientBoosting, 200 rounds, no hyperparameter search), one seed, 60 fit questions, MATH level-5 only; HumanEval is a transfer. A feature set that fails with this learner might pass with more data or tuning. (4) Collection has no first-EOS truncation (as the original fit and the refit), evaluation arms do. (5) The fit pipeline is the refit's reconstruction of the original fitter, not the original. (6) Nothing here applies to the 16-window shape; features of kind H and `kl_prev` are defined for any shape but only R-S32c was collected. (7) Token-class tables depend on the tokenizer decode of a single token; byte-fragment tokens are 0.
